# 상자·럭키몬스터의 월드 드롭

몬스터 사망, 상자 개봉, 럭키몬스터 타격은 발생 조건만 다르게 하고
`RPGWorldLoot`의 서버 생성과 기존 `ARPGPickUpBase`의 착지·획득 연출을 공유한다.
클라이언트는 확률·수량·재화 코드·수령인을 전송하지 않는다.

## 작성과 연결

| 대상 | 작성 방법 | 서버 발생 조건 |
|---|---|---|
| 보물상자 | `ARPGTreasureChest` 자식 Blueprint에 메시, LootSource의 DropTable/DropRow 설정 | 기존 상호작용 입력으로 개봉, 액터 수명 중 1회 |
| 럭키몬스터 | `ARPGLuckyMonster` 자식에 기존 NPC 시작 데이터·메시·HitLoot의 표/행 설정 | 적대 플레이어에게 실제 체력이 감소한 피해, 간격/총횟수 제한 |
| 기존 NPC | 기존 드롭 Ability와 표 유지 | 기존 사망·서버 권한 검사 및 액터 수명 중 1회 |
| 재화 드롭 | `ARPGCurrencyPickup` 자식에 메시·CurrencyCode·AmountPerUnit 설정 후 같은 드롭 표의 ItemClass에 지정 | 기존 지갑 거래로 확정된 뒤 픽업 제거 |

`FItemDropTable` / `FDropItem`의 기존 확률과 수량을 사용한다. 일반 아이템은 기존
Manifest·정의·중첩 수량 계약을 유지한다. 재화의 실제 금액은 `DropQuantity × AmountPerUnit`이며
코드 형식, 양수, Int64 곱셈 오버플로를 검사한다. 현행 상호작용 수량 타입에 맞춰
표의 DropQuantity는 1~127이다. 재화 정의/소유 범위/상한/활성 여부는 기존 백엔드가 결정한다.

상자 기본 상호작용은 즉시 개봉이다. 미정 메시·드롭 내용·재화 정의를 자동으로 만들지 않는다.
기존 맵이나 몬스터 Blueprint를 새 보상으로 자동 교체하지 않으며, 작성한 자식을 배치해야 한다.
상자는 ChestMesh에 작성한 메시의 충돌을 사용한다. 럭키 타격 드롭 외에 사망 보상도 필요하면
기존 사망 Ability를 별도로 작성한다. 타격과 사망은 각각의 명시적인 보상이다.

## 발생 권한과 단일 실행

개봉 RPC는 소유 플레이어 컨트롤러의 `URPGLootInteractionComponent`에 있다.
공유 상자/픽업의 소유권을 플레이어에게 이전하지 않는다. 서버에서 대상 월드, 원래 액터 ID,
인증/회수 상태, 현재 Pawn, 거리 250cm, 벽, 사망·탑승 상태를 검사한다.
상자 ID와 사용 횟수는 복제하며, 클라이언트의 개봉 요청은 이미 열린 상자를 재추첨하지 못한다.

획득을 선점한 픽업과 이미 열린 상자는 상호작용 키의 탐색 대상에서 제외된다.
시간이 설정된 아이템·재화 픽업은 서버가 시작을 승인할 때 액터를 한 플레이어에게 예약한다.
다른 플레이어의 시작과 직접 획득 요청을 거절하며, 예약 복제 후에는 탐색 목록에서도 빠진다.
서버가 진행 완료를 확인하면 예약을 유지한 채 기존 획득 처리에 넘긴다. 취소, 범위 이탈,
빙의 변경, 연결 종료로 진행이 끝나면 살아 있는 동일 드롭의 예약을 해제한다.

럭키 타격은 `URPGAttributeSet::PostGameplayEffectExecute`의 실제 TakeDamage 처리에 연결한다.
대상 NPC/ASC 일치, 원래 공격자 ASC와 현재 플레이어 소유권, 적대 팀, 3000cm/벽,
유한한 체력 감소를 확인한다. 회복·0 피해·완전 방어·이미 죽은 대상은 드롭하지 않는다.
기본 간격 0.15초, 최대 10회이며 작성 허용 범위는 간격 0.05~60초, 최대 1~100회다.
처치에 이르는 마지막 타격도 유효 피해 1회다. 치유/재호출로 예산을 초기화하지 않는다.

표 전체를 검증·복사하고 발생 횟수를 먼저 소비한 다음 생성한다. 확률에 모두 빗나가거나
생성이 실패해도 완료한 사건을 다시 굴리지 않는다. 생성/Construction 콜백의 재진입도
같은 예산을 넘지 못한다. 표의 누락/잘못된 설정은 발생 전 거절한다.
분산 착지 지면·벽 검사, 서버 시간의 비행 중 획득 거절, 등급/사운드는
[기존 드롭 연출 계약](ITEM_LOOT_PRESENTATION.md)을 따른다.

## 재화 픽업의 지갑 반영

재화는 인벤토리 슬롯을 사용하지 않는다. 전용 서버의 기존
`URPGEconomyBackendSubsystem` / Gateway / `/api/economy/transactions/commit`을 사용한다.
`requestId`는 서버 Drop ID, operation은 `WorldLoot`, reason은 `World.Loot.Currency`다.
첫 수령 시 원래 캐릭터/세션/통화/금액을 고정한다. 기존 백엔드 영수증의 요청 ID·전체 명령
대조와 지갑 원자 반영으로 동일 요청 재전송을 단일 지급으로 처리한다.
확정 거래 알림은 기존 PlayerState의 새 지갑 조회/소유자 복제를 갱신한다.
일반 아이템 픽업 RPC에 재화 액터를 전달하는 우회도 거절한다.

POST 전에 `Saved/CurrencyLoot/<session-guid>/<drop-guid>.json`에 원래 정규 본문을
flush·비교체 rename으로 기록한다. Windows에서 같은 드롭의 파일 lock을 액터 수명 동안
보유한다. 다른 기록/동시 소유자/링크/저장 실패는 새 전송 전에 거절한다. 토큰은 저장하지 않는다.
성공 영수증과 원래 금액이 일치하고 기록 삭제까지 성공해야 픽업을 정리한다.

응답 유실·오류·거절 뒤에는 기존 지급의 미반영을 추측하지 않는다. 픽업과 원래 요청을
잠근 채 같은 명령으로만 재시도한다. 각 Gateway 호출은 기존 최대 시도 정책을 쓰며,
액터는 최대 5회 호출/지수 간격을 사용한다. 각 후속 호출 전에 같은 Controller/PlayerState,
계정/캐릭터/세션/연결 세대·현재 상호작용 권한을 다시 확인한다.
종료나 신원 변경은 추가 POST를 멈추고 원래 기록을 보존한다. 늦은 성공은 원래 지급의
확정으로만 처리하며 다른 캐릭터에게 재할당하지 않는다.

이 기능은 월드 상자/처치/미획득 드롭의 영속 복원이나 호스트 이관을 추가하지 않는다.
종료 뒤 남은 재화 기록은 원래 사건의 복구 근거이며, 새 액터로 자동 채택/재지급하지 않는다.
미확정 액터는 다른 수령인에게 풀지 않으므로 장애 시 지급 지연/잠금은 있을 수 있다.

## 집중 검증

- `Scripts/Tests/Run-LootSourceTests.ps1`: 게시 소스 사본에 본인 변경만 합쳐 전체 UHT/CPP
  컴파일·Editor 링크 후 상자/럭키/재화 native 검사와 기존 NPC/대검 픽업 회귀를 실행한다.
  `-CompileOnly`는 전체 타깃의 UHT 및 영향 CPP 컴파일만 수행한다.
  `-InstalledSnapshot`은 정상 출력의 사본을 사용하며 DLL/PDB GUID 및 모든 본인 입력의
  컴파일러 SHA-256이 일치해야 실행한다. `-InstalledBinaryRoot`로 별도 검증 출력을 지정할 수 있다.
- `Scripts/Tests/Run-LootCurrencyHttpTests.ps1`: 실제 loopback Kestrel/인증/Memory 저장소에서
  커밋 응답 유실, 같은 ID 병렬 재전송, 수령인/금액 변경 거절, 지갑 상한/비활성/멤버십을 검사한다.

두 실행기는 자기 Saved/LS/GUID 사본·빌드·DLL·캐시·UserDir를 종료 후 정리하고
작은 Saved/BuildChecks/LootSources-20261116 결과만 남긴다. 공유 에디터/원본 출력은 사용하지 않는다.
이 검사는 실제 작성 상자/럭키의 자연 전투·물리 입력·다인 Steam·PostgreSQL·Shipping 패키징의
완료 증거가 아니다. 구체적인 실행 결과는 검증 완료 후 이 문서와 로드맵에 기록한다.

### 2026-11-17 확인 결과 (11월 16일 착수)

- 실제 HTTP/인증/Memory 검사 24 assertion이 통과했다. 커밋 응답 1회 유실 뒤
  같은 요청의 병렬 4회 재전송은 원래 영수증만 반환했다. 수령인/금액 변경, 비멤버,
  비활성 통화, 상한 초과, 포기한 멤버를 거절하고 남은 멤버의 정상 지급을 유지했다.
  독립 Release 빌드 오류/경고 0이다.
- 첫 사설 UHT/CPP 검사에서 선언/API 연결 문제를 보정했다. 이후 다른 담당자의
  정상 Build12 전체 Editor 링크 성공을 재사용했다. `8C2CF00D…04E707B` DLL과 PDB GUID가
  일치하며 본인 소스/유지 검사 입력 22개의 SHA-256이 컴파일러 기록과 전부 같았다.
  별도 전체 빌드의 중복 실행은 중단하고 사본만 실행했다.
- 해당 사본에서 상자/재화/표 검증 3개와 기존 NPC/대검 6개가 성공했다.
  럭키 fixture의 시작 데이터 누락 ensure는 성공으로 세지 않았다. 테스트 CPP에서만
  빈 시작 데이터를 명시한 뒤 사설 CPP 컴파일/링크를 수행했다. 제품 입력 21개는
  바뀌지 않았고, 최종 `95766FB2…5B35F734`의 본인 입력 22개 PDB 대조와 실제
  LuckyDamageBudget 검사 1개가 오류/경고 0·프로세스 exit 0으로 통과했다.
  다른 9개의 이미 통과한 검사는 반복하지 않았다.
- 기존 무효 NPC 표의 의도한 거절 경고 6개를 유지한다. 마지막 실행의 기존 콘텐츠 로드
  오류 15줄은 초기 실행에도 모두 있던 메시지이며 새 오류 0/ensure 0이다.
  이를 프로젝트 전체 콘텐츠가 정상이라는 주장으로 확대하지 않는다.
- 자기 사본/OBJ/DLL/PDB/캐시/UserDir/링크를 총 10,205,814,800 bytes (9.505GiB)
  폐기했다. Saved/LS 잔여·소유 프로세스·정리 예외는 없고 작은 결과/명령/해시만 보존한다.

근거는 `Saved/BuildChecks/LootSources-20261116/Completion.json`에 묶었다.
폐기한 바이너리의 해시는 당시 검증 증거이며 재실행 가능한 출력이 남았다는 뜻이 아니다.
이는 공유 Build12와 본인 fixture CPP/링크의 범위이며 현재 전체 트리의 자체 빌드 완료는 아니다.
