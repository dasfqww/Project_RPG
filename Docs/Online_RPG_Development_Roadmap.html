# Project_RPG 온라인 전환 및 출시 로드맵

작성일: 2026-07-14  
대상 엔진: Unreal Engine 5.8  
문서 상태: 초안 1.0

## 1. 문서 목적

이 문서는 `Project_RPG`를 전투 중심 싱글플레이 프로토타입에서 2~4인 협동 온라인 액션 RPG로 발전시키기 위한 기준 문서다. 기능을 무분별하게 늘리는 대신, 데디케이티드 서버와 Iris 기반 복제를 학습하면서 실제로 출시 가능한 범위를 유지하는 것이 목적이다.

## 2. 결론

현재 프로젝트는 온라인 RPG를 처음부터 만드는 상태가 아니다. GAS 전투, 캐릭터, AI, 인벤토리, 장비, 퀵슬롯, UI, Game Features 등 상당한 기반이 이미 존재한다.

그러나 깨진 에셋 참조, Asset Manager 설정 충돌, 미완성 장비·인벤토리 로직, 저장 시스템 부재 등이 있어 곧바로 온라인 기능을 확장하면 디버깅 비용이 매우 커진다.

권장 제품 범위는 다음과 같다.

- 플랫폼: Windows PC
- 형태: 2~4인 협동 액션 RPG
- 구조: 로비 → 전투 스테이지 또는 웨이브 → 보스 → 보상 → 로비 복귀
- 캐릭터: 초기 1종
- 무기군: 초기 1종(대검)
- 적: 일반 적 3~4종, 보스 1~2종
- 서버: Dedicated Server
- 복제: Iris 기본 복제부터 시작
- 초기 연결: 직접 IP
- 후속 연결: EOS 또는 Steam 세션

## 4. 목표 네트워크 구조

`Dedicated Server + Iris + GAS + 세션/로비 서비스`를 기본 구조로 사용한다.

각 기술의 역할은 다음과 같다.

- Dedicated Server: 게임 규칙과 결과를 결정하는 권위 서버
- Iris: 액터와 상태를 클라이언트에 복제
- GAS: 능력 활성화, 효과, 속성, 예측을 관리
- Replication Graph: 필요할 때 액터 관심 영역과 복제 규모를 최적화
- EOS 또는 Steam: 로그인, 세션 검색, 로비, 초대와 참가를 제공

Iris와 Replication Graph를 처음부터 동시에 깊게 커스터마이징하지 않는다. 2~4인 플레이에서는 Iris 기본 복제로 기능을 완성하고, 프로파일링 결과가 요구할 때 최적화한다.

## 5. 서버 권위 원칙

다음 결과는 반드시 서버가 결정한다.

- 플레이어 및 AI의 체력 변화
- 공격 적중과 최종 데미지
- Ability 활성화 가능 여부와 비용
- 사망, 부활, 보상 및 드롭
- 아이템 획득, 이동, 분할, 소비 및 장착
- 장비가 부여하는 Ability와 Attribute
- 웨이브 진행과 보스 상태
- 퀘스트나 스테이지 완료 조건

클라이언트는 입력, 예측, 카메라, UI와 연출을 담당한다. 클라이언트가 보낸 RPC는 요청으로 취급하며 서버가 거리, 소유권, 수량, 쿨다운과 현재 상태를 검증한다.

## 6. 알려진 기술 부채

온라인 작업 전에 아래 문제를 우선 처리한다.

### 프로젝트 및 설정

- Live Coding이 활성화되어 커맨드라인 빌드가 차단됨
- `.uproject`에 `GameFeatures`, `ModularGameplay` 의존성이 명시되지 않음
- deprecated된 `StructUtils` 의존성 존재
- Game Feature와 프로젝트 간 `Map` Primary Asset 설정 충돌
- `/Script/D1Game` 및 `LyraExperienceDefinition` 잔존 참조
- `GladiatorCore`가 존재하지 않는 Game Feature Action 클래스를 참조
- Meshy 플러그인에 잘못된 include 경로 경고 존재

### 에셋 및 데이터

- `BT_Guardian.uasset` 로드 불가
- `DT_ItemInfo`의 RowStruct 누락
- 퀵슬롯 입력 Gameplay Tag 일부가 유효하지 않음
- HUD와 퀵슬롯 UI에 누락된 의존 패키지 존재
- 포션 메시와 머티리얼의 의존 에셋 누락
- 포션 머티리얼 컴파일 실패

### 기능 구현

- 장비 외형 스폰과 장비 Ability 부여 미완성
- 인벤토리 아이템 소비의 서버 처리 미완성
- 생존 모드의 다음 적 스폰 처리 미완성
- 스킬 창의 실제 데이터 로드 미완성
- 옵션 저장·로드 미완성
- SaveGame 시스템 부재
- 실질적인 퀘스트, 대화, 상점 시스템 부재

## 7. 단계별 개발 계획

### 단계 0: 기준선 복구

목표: 네트워크 오류와 기존 프로젝트 오류를 분리할 수 있는 상태를 만든다.

작업:

1. 에디터와 Live Coding을 종료한다.
2. `Project_RPGEditor Win64 Development` 클린 빌드를 성공시킨다.
3. 시작 로그의 프로젝트 관련 Error와 Ensure를 제거한다.
4. 깨진 Game Feature와 이전 프로젝트 참조를 수정하거나 격리한다.
5. Gameplay Tag, DataTable, UI와 아이템 참조를 복구한다.
6. 현재 싱글플레이 전투가 정상 동작하는지 확인한다.

완료 조건:

- 에디터 타깃 빌드 성공
- 에디터 시작 시 프로젝트 소유 Error/Ensure 0개
- 테스트 맵에서 이동, 공격, 피격과 사망 확인

### 단계 1: 최소 데디케이티드 서버

목표: 별도 서버와 두 클라이언트가 같은 월드에 접속한다.

작업:

1. `Project_RPGServer.Target.cs`를 추가한다.
2. `/Game/Maps/NetTestMap`을 만든다.
3. PlayerStart 4개와 단순한 바닥만 배치한다.
4. 테스트용 GameMode와 플레이어 Pawn을 지정한다.
5. 초기에는 직접 IP로 접속한다.

완료 조건:

- 데디케이티드 서버 빌드와 실행 성공
- 클라이언트 2개가 `127.0.0.1`로 접속
- 서로의 이동과 회전을 확인
- 접속 종료 시 Pawn이 정상 정리됨
- 서버 로그에 프로젝트 관련 Error 없음

### 단계 2: 서버 권위형 전투

목표: 두 플레이어가 같은 적을 공격하고 서버가 결과를 일관되게 결정한다.

작업:

1. ASC 초기화와 Attribute 복제를 검증한다.
2. 기본 공격과 스킬 활성화를 서버 권위 구조로 정리한다.
3. 근접 적중, 투사체와 데미지를 서버에서 판정한다.
4. 사망, 부활과 Gameplay Cue를 복제한다.
5. 높은 지연과 패킷 손실 환경에서 테스트한다.

완료 조건:

- 모든 클라이언트에서 체력과 사망 상태가 일치
- 중복 적중과 중복 보상 없음
- 클라이언트가 임의 RPC로 데미지나 Ability 비용을 조작할 수 없음
- 100~150ms 지연에서도 플레이가 가능한 수준

### 단계 3: 인벤토리와 장비

목표: 아이템 상태를 서버가 소유하고 모든 플레이어가 일관된 결과를 본다.

작업:

1. FastArray 기반 아이템 복제를 검토하고 완성한다.
2. 획득, 이동, 스택, 분할, 소비와 버리기를 서버 RPC로 처리한다.
3. 장비 슬롯 검증과 외형 복제를 구현한다.
4. 장비 Ability 부여 및 제거 핸들을 관리한다.
5. 동시 획득과 중복 소비를 방지한다.

완료 조건:

- 동일 아이템을 두 사용자가 동시에 획득할 수 없음
- 재접속 전까지 서버와 소유 클라이언트의 인벤토리가 일치
- 장비 외형, Attribute와 Ability 상태가 모든 클라이언트에서 일치

### 단계 4: AI와 협동 콘텐츠

목표: 서버에서 AI와 웨이브·보스전을 운영한다.

작업:

1. AIController, Behavior Tree와 스폰 로직을 서버 전용으로 실행한다.
2. 어그로와 타깃 선택을 다중 플레이어에 맞춘다.
3. 웨이브 진행과 보스 상태를 GameState로 복제한다.
4. 보상과 스테이지 결과를 서버에서 확정한다.

완료 조건:

- 두 플레이어가 참가한 보스전 한 판을 처음부터 끝까지 완료
- 중도 퇴장 시에도 전투가 진행 불가 상태에 빠지지 않음
- 승리, 실패와 보상이 모든 클라이언트에서 일치

### 단계 5: 로비와 온라인 서비스

목표: 직접 IP 없이 게임을 만들고 참가한다.

작업:

1. EOS 또는 Steam 중 하나를 선택한다.
2. 세션 생성, 검색, 참가와 종료를 구현한다.
3. 로비 준비 상태와 맵 이동을 처리한다.
4. 접속 실패, 서버 종료와 타임아웃 UI를 구현한다.

완료 조건:

- 서로 다른 PC에서 세션 생성과 참가 성공
- 로비에서 전투 맵으로 Server Travel 성공
- 게임 종료 후 로비 또는 메인 메뉴로 안전하게 복귀

### 단계 6: 출시 안정화

목표: 외부 사용자가 설치하고 한 판을 안정적으로 끝낼 수 있다.

작업:

1. Shipping 서버와 클라이언트를 패키징한다.
2. SaveGame 또는 서버 저장 정책을 확정한다.
3. 크래시, 진행 불가와 악용 가능한 RPC를 점검한다.
4. 네트워크, CPU와 대역폭을 프로파일링한다.
5. 외부 플레이테스트를 반복한다.
6. 사용 에셋과 플러그인의 배포 라이선스를 확인한다.

완료 조건:

- 별도 PC 환경에서 설치·접속·플레이·종료 성공
- 최소 30분 세션 반복 테스트 통과
- 치명적 크래시 및 진행 불가 0건
- 출시 대상 하드웨어에서 목표 프레임과 서버 틱 유지

## 8. 첫 번째 마일스톤

첫 번째 네트워크 마일스톤은 다음 한 문장으로 고정한다.

> 데디케이티드 서버 1개와 클라이언트 2개가 NetTestMap에 접속하여 서로 이동하는 모습을 확인한다.

이 마일스톤에는 인벤토리, 보스, 복잡한 UI, Steam/EOS와 Replication Graph 최적화를 포함하지 않는다.

## 9. 테스트 원칙

- 멀티 PIE 성공만으로 완료 처리하지 않는다.
- 별도 서버 프로세스와 별도 클라이언트 프로세스로 검증한다.
- 최소 두 대의 PC 또는 실제 외부 네트워크에서 검증한다.
- `Net PktLag`, `Net PktLoss` 등으로 지연과 손실을 재현한다.
- 서버 로그와 클라이언트 로그를 각각 보관한다.
- 기능마다 정상 경로뿐 아니라 중도 퇴장, 중복 요청과 잘못된 요청을 시험한다.
- 중요한 게임 상태는 서버 값과 각 클라이언트 표시 값이 일치하는지 확인한다.

## 10. 범위 통제 원칙

첫 출시 전에는 다음 기능을 보류한다.

- 오픈월드
- 대규모 동시 접속
- 여러 직업과 다수 무기군
- PvP 및 랭킹
- 복잡한 제작과 경제 시스템
- 절차적 대규모 던전
- 커스텀 Iris 최적화
- 필요성이 측정되지 않은 Replication Graph 확장

새 기능을 추가하기 전에 현재 마일스톤의 완료 조건을 먼저 충족한다.

## 11. 의사결정 기록
