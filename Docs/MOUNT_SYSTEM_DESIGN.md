# 탈것 시스템 작업 계획 — 로스트아크 벤치마크

- 작성일: 2026-11-06
- 상태: **설계 초안 / 게임 기능 미구현**
- 담당 기록: `mount-design-20261105` (작업 시작일 기준)

사용자 확정 방향은 **로스트아크의 탈것 시스템을 벤치마킹하고, 작업 방법을 문서로 정리한다**는 것이다.
아래 구조·정책·작업 순서는 구현 제안이다. 실제 클래스와 저장 형식이 이미 존재하거나 제품 정책이 모두 확정됐다는 뜻은 아니다.
이 문서를 구현과 인계의 기준으로 유지하고, 구현이 진행되면 완료 범위와 달라진 결정을 갱신한다.

## 1. 참고할 경험과 근거

플레이 흐름은 **획득 → 보관함 등록 → 선택/퀵슬롯 탑승 → 빠른 이동·전용 액션 → 하차**로 잡는다.

| 참고 항목 | 확인한 사실과 적용 방향 |
|---|---|
| 즉시 탑승 | 한국 공식 2026-11-04 업데이트는 소환 모션을 없애고 즉시 탑승하도록 변경했다. 우리도 서버 승인 후 즉시 전환을 기본안으로 한다. |
| 교체 시 쿨타임 | 같은 업데이트에서 다른 탈것으로 바꾸어도 이동기의 남은 쿨타임이 적용된다. 하차·재탑승·교체로 이동기를 연속 사용하는 우회를 막는다. |
| 보관함·퀵슬롯 | 공식 대만 가이드는 아이템 사용으로 보관함 등록, 보관함/퀵슬롯 탑승을 설명한다. UI 진입점은 달라도 동일한 서버 명령을 사용한다. |
| 전용 액션 | 가이드는 Space 이동기, 일부 탈것의 추가 이동기와 감정표현을 설명한다. 탈것별 액션 목록을 데이터로 정의한다. |
| 즐겨찾기 | 즐겨찾기와 무작위 소환을 보관함 후속 기능으로 둔다. 무작위 후보는 보유·현재 구역 사용 가능 조건을 모두 만족해야 한다. |

서비스 지역·업데이트 시점이 다르므로 대만 가이드의 지역 제한을 현재 한국 규칙으로 단정하지 않는다.
**전투 중 소환 가능 여부, 일반 피격/상태이상에 따른 하차, NPC 상호작용, 맵 이동 후 유지 여부는 아직 확인하지 않았다.**
앞선 대화의 “전투 중 소환 금지·피격 즉시 하차”는 제안이었으며 로아에서 확인한 규칙이 아니다.
벤치마크는 플레이 경험의 참고이며 로아 내부 구현을 추정해 사실로 기록하지 않는다.

## 2. 첫 범위와 구현 전에 정할 정책

첫 범위는 1인용 지상 탈것, 즉시 탑승/하차, 전용 이동기 1개, 보유 등록·선택·퀵슬롯,
전용 액션 표시와 다른 플레이어에게 보이는 탑승 외형까지다.
다인승·탈것 자체 HP/독립 AI·기마전투·자유 비행은 이번 초안의 구현 범위에 포함하지 않는다.

| 결정 항목 | 권장안 / 남은 확인 |
|---|---|
| 기본 이동속도 | 탈것 간 통일을 권장. 수치는 플레이 테스트로 정하고 캐릭터 전투 이동속도 버프의 적용 여부를 명시한다. |
| 이동기 차이 | 공통 실행기에 거리·시간·횟수·쿨타임·모션을 데이터로 전달. 첫 버전은 단일 돌진부터 시작한다. |
| 보유 공유 범위 | 계정+게임서버(원정대에 해당하는 범위) 공유 권장. 기존 인증·캐릭터 소유 계약에 맞춰 저장 키를 확정한다. |
| 선택·즐겨찾기 | 캐릭터별 선택과 공유 보유 목록을 분리. 즐겨찾기 공유 범위는 보관함 작업 때 결정한다. |
| 탑승 조건 | 전투·시전·피격·상태이상·상호작용별 규칙을 M0에서 확인하고 표로 확정한다. 확인 전 임의의 로아 규칙을 구현하지 않는다. |
| 지역 제한 | 맵 기본 정책+구역별 금지/허용 예외. 던전이라는 이유만으로 일괄 금지하지 않는다. 충돌하는 구역의 우선순위도 정한다. |
| 하차와 수명 | 사망/권한 폐기/월드 종료 시 진행 액션 정리는 필수. 일반 피격, 여행·재접속 시 탑승 및 쿨타임 복원 정책은 M0에서 결정한다. |
| 외형·충돌 | 초기 탈것의 크기 범위를 제한하고 이동 충돌은 하나로 유지. 긴 모델의 벽 관통 허용 정도와 캡슐 크기는 에셋 단계에서 확인한다. |

## 3. 프로젝트에 연결할 구조

**기존 플레이어 Pawn과 ASC를 유지하고, 탑승 상태·외형·액션을 추가하는 구조를 권장한다.**
현재 [RPGBaseCharacter](../Source/Project_RPG/Private/Character/RPGBaseCharacter.cpp)는 ASC를 직접 소유하고,
[이동 컴포넌트](../Source/Project_RPG/Private/Component/RPGCharacterMovementComponent.cpp)는 GAS 이동속도와 행동 제한을 계산한다.
2026-11-06 읽기 당시 게시 HEAD는 `3346d2f`였으며 일부 공통 소스는 다른 담당이 수정 중이었다. 구현 착수 때 다시 확인한다.

아래 새 이름과 경로는 후보이며 아직 구현된 API가 아니다.

| 구성 | 책임 / 후보 위치 |
|---|---|
| `RPGMountDefinition` | ID·버전, 표시 이름/아이콘, 모델/AnimBP, 탑승 자세/오프셋, 이동 설정, 액션 목록, 구역 분류. 신규 `Source/Project_RPG/{Public,Private}/Mount/` |
| `RPGMountComponent` | 서버의 보유/구역/상태 검사, 탑승·교체·하차, 복제 상태, 자기 능력·입력 핸들의 수명 관리. 같은 Mount 경로 |
| `RPGMountPresentationComponent` | 복제 상태에 따른 모델·탑승 자세·카메라·효과음. 비동기 로드 완료 시 상태 세대를 재확인 |
| 탈것 액션 Ability | 기존 ASC에서 이동기·감정표현 실행. 직업 스킬 편성/성장 조건과 분리하고 자기 grant만 해제 |
| 기존 이동 컴포넌트 | 탑승용 속도/가속/회전과 행동 제한의 최종 계산, 예측·서버 재현·충돌 처리 |
| 보관함·전용 액션 UI | 보유/선택/쿨타임을 읽고 명령 전달. 후보 `UI/Mount/`, `Content/Blueprints/Mount/` 및 HUD 모듈 |
| 백엔드 탈것 기능 | 공유 보유 목록·선택·즐겨찾기와 등록 트랜잭션. 후보 `Backend/ProjectRpg.Backend/Mounts/`; 실제 DB migration 번호는 착수 때 배정 |

기능이 작을 때부터 모든 역할을 별도 계층으로 쪼개지는 않는다. 상태 판단, 이동 실행, 외형 표시, 영속 저장의 책임을 구분한다.

### 이동·복제

- 상태의 기본 흐름은 `OnFoot ↔ Mounted`. 서버 승인 대기는 요청 처리 상태이며 강제 소환 시전시간으로 취급하지 않는다.
- 서버 확정 탈것 ID·상태·전환 세대를 복제한다. 중도 접속/다시 시야에 들어온 클라이언트가 현재 상태만으로 외형을 복원할 수 있어야 한다.
- 소유 목록·즐겨찾기는 소유자에게만 제공한다. 타 플레이어에게는 현재 외형·액션에 필요한 상태만 보낸다.
- 탑승자와 탈것 외형은 같은 이동·네트워크 스무딩 기준을 따른다. 별도 탈것 외형이 독립 이동/충돌을 수행해 캐릭터와 충돌하지 않도록 한다.
- 속도는 기존 `GetMaxSpeed()` 계산에 명시적으로 통합한다. 탑승 전후의 설정을 저장 이동(SavedMove) 재실행에서도 일관되게 재현하며 전환 전후 이동의 부적절한 합치기를 막는다.
- 이동기는 기존 CMC/Root Motion Source 등 이동 경로와 서버 승인 예산에 연결한다. [AuthorizedMovement](../Source/Project_RPG/Public/Ability/AbilityTask/AbilityTask_AuthorizedMovement.h)는 **이동 허용 창**이며 실제 이동/충돌/예측을 구현해주는 기능이 아니다.
- 기존 직업 스킬 정의를 읽는 helper를 탈것에 그대로 적용하지 않는다. 서버 소유 탈것 정의에서 유한 거리·시간 예산을 얻는 연결을 추가한다. 상시 보안 면제나 클라이언트 지정 속도/거리를 허용하지 않는다.
- 캡슐 변경/하차 위치 조정이 필요하면 서버 sweep과 바닥 검사를 거친다. 벽·천장·경사·낭떠러지 경계에서 허용되지 않는 위치로 이동시키지 않는다.
- 복제보다 늦게 끝난 모델 로드, 취소된 액션 콜백, 오래된 교체 응답은 전환 세대/소유자 재확인으로 무시한다.

### 입력·HUD·쿨타임

- 탑승 중에는 전용 입력/액션 표시를 활성화한다. **기존 스킬 편성 저장값을 탈것 액션으로 덮어쓰지 않는다.**
- 키 변경을 존중하고 Space/Q/R을 코드 곳곳에 고정하지 않는다. 전환 시 누르고 있던 스킬 입력을 해제하고, 종료 때 자기 바인딩만 제거한다.
- [현재 퀵슬롯](../Source/Project_RPG/Public/Component/UI/QuickSlotComponent.h)은 스킬과 아이템 중심이다. 탈것 호출 항목/전용 바 연결이 이미 지원된다고 가정하지 말고 저장 형식·입력·UI를 함께 설계한다.
- [HUD 모듈 계약](PLAYER_HUD_MODULARIZATION.md)에 맞춰 탈것 액션 모듈을 연결한다. [옵션 UI 입력 소유](OPTIONS_UI_INPUT_OWNERSHIP.md)와 다른 창의 포커스를 보존한다.
- 이동기의 서버 쿨타임 종료시각을 단일 기준으로 삼는다. UI 타이머는 표시용이며 하차·외형 삭제·다른 탈것 교체로 종료시각을 초기화하지 않는다.
- GAS 효과와 별도 타이머가 각각 다른 정답을 갖지 않도록 쿨타임 소유를 하나로 정한다. Pawn 교체/재접속까지 유지할 정책이라면 캐릭터 식별자로 인계·복원하는 경로도 구현한다.
- 서버에서 탑승 상태·허용 액션·쿨타임을 검사한다. HUD에서 전투 버튼을 숨기는 것만으로 전투 능력 사용을 막았다고 간주하지 않는다.

### 영속 저장

- 아이템 사용으로 등록할 때는 **아이템 소비 + 탈것 해금 + 요청 영수증**을 같은 서버 트랜잭션에서 확정한다.
- [아이템 액션 계약](ITEM_ACTION_TRANSACTIONS.md)의 요청 ID·내용 지문·리비전 검증을 따르되, 기존 소비 성공 후 클라이언트 콜백으로 영구 해금하는 방식은 사용하지 않는다.
- 같은 요청의 재전송은 최초 결과를 반환한다. 다른 캐릭터가 동시에 같은 공유 탈것을 등록하는 경우에도 중복 소비를 막는다. 이미 보유한 탈것의 등록 아이템은 소비하지 않는 안을 권장한다.
- 보유 범위는 인증 계정/서버/캐릭터 소유 관계에서 결정한다. 클라이언트가 보낸 보유 여부나 계정 ID를 권한으로 신뢰하지 않는다.
- 게임 서버는 승인된 보유 정보를 받아 탑승을 검사한다. 이동 매 프레임에 백엔드를 호출하지 않는다.
- 영속 데이터에는 보유 ID·선택·즐겨찾기·리비전 등을 저장한다. Actor 포인터, 일시적인 모델 로드 상태, 매 프레임 위치는 탈것 보관함 데이터에 저장하지 않는다.

## 4. 작업 순서와 각 단계의 완료 기준

각 단계는 필요한 검증·자기 임시 산출물 정리 후 기능별 커밋·푸시·원격 반영 확인까지 끝낸다.
다음 표는 예정 작업이며 체크되지 않은 항목은 구현 완료가 아니다.

| 단계 | 작업 | 완료 기준 |
|---|---|---|
| M0 | 탑승 조건·지역·하차/쿨타임 수명, 보유 공유 범위 확정. 최신 조율/계약/호출 재확인 | 확인된 벤치마크와 우리 정책을 구분한 규칙표, 수정 경로와 담당 의존성 확보 |
| M1 | 공통 정의·MountComponent·탈것 1종으로 탑승/하차·외형 복제 | 서버+클라이언트 2개에서 본인/상대 외형, 중도 접속, 취소/종료, 기본 충돌 확인. 개발용 보유 fixture는 제품 권한 경로와 분리 |
| M2 | 이동기 1개, 서버 쿨타임, 입력 전환·전용 HUD | 지연/유실 조건에서 이동·벽 충돌·기존 스킬 차단, 하차/교체 쿨타임 유지, 원래 입력/편성 복원 |
| M3 | 등록 아이템·영속 보유·선택 API와 실제 보관함/퀵슬롯 연결 | 실제 인증으로 획득→등록→탑승→재접속 복원. 응답 유실 재시도·동시 등록·다른 계정 거절 확인 |
| M4 | 즐겨찾기/무작위·전용 모션·두 번째 탈것과 구역 정책 연결 | 정의/에셋 추가로 두 번째 탈것 적용, 구역별 후보 필터, 로드 실패/빠른 교체/사용 제한 표시 확인 |
| M5 | 실제 맵·전투/상호작용·여행/재접속 통합 마무리 | M0 정책표와 실제 플레이 일치, 필요한 cook 참조·에셋 로드·대상 패키지 검증, 미검증 범위 명시 |

M1~M2가 끝나도 영속 보유/제품 입력 연결이 없으면 “탈것 시스템 전체 완료”로 보고하지 않는다.
첫 이동기는 실제 탈것 모델이 준비되기 전 임시 외형으로 개발할 수 있으며, 최종 탑승 자세/애니메이션 검증은 실제 에셋으로 수행한다.

## 5. 검증에서 놓치지 않을 사례

- 탑승/하차/교체 연타, 중복 요청, 전환 중 사망·권한 폐기·접속 종료, 오래된 비동기 로드 완료.
- 클라이언트의 미보유 탈것 ID·임의 액션·쿨타임/속도/목적지 조작 거절.
- 지연 80~160ms와 패킷 유실 5%를 예시 조건으로 사용해 본인 이동 보정·상대 스무딩·중도 접속 확인. 실제 사용 조건에 맞게 조정.
- 벽·좁은 문·천장·계단·경사·낭떠러지·탑승 금지 구역 경계에서 이동기/하차 확인.
- 탑승 중 키 변경·옵션 창·포커스 전환·누른 키 해제, 하차 후 HUD/편성/입력 복원.
- 아이템 소비와 해금의 원자성, 응답 유실 재시도, 공유 보유 동시 등록, 백엔드 재시작.
- 두 번째 탈것/스킨 교체 시 이전 모델·소리·카메라·능력 핸들 잔존과 쿨타임 초기화가 없는지 확인.
- 단위/native 검사, 실제 네트워크 실행, 실제 에셋/GPU 표시, 패키징 결과를 구분해 보고.

## 6. 다음 담당자가 착수할 때

1. [AGENTS.md](../AGENTS.md)와 [로드맵 12절/작업 조율](Online_RPG_Development_Roadmap.md)을 다시 읽는다.
2. 이번 문서 작성은 제품 소스 예약이 아니다. 실제 수정할 Source/Backend/에셋/검사·공유 빌드 자원을 별도로 예약하고 재조회한다.
3. 읽기 당시 Character/UI 계약, Controller 입력, HttpWebManager 복구는 SOLID 작업과 겹쳤다. 최신 완료/인계를 확인하고 공통 파일을 동시에 수정하지 않는다.
4. 기존 [아이템 저장 경계](ITEM_BACKEND_GATEWAY.md), HUD·입력 계약 및 실제 호출을 재확인한다. 명칭이 같은 새 관리자를 중복 구현하지 않는다.
5. 검증용 사본/출력 경로를 시작 전에 정하고 종료 정리를 실행기에 넣는다. 원본 Binaries/Intermediate·공유 DDC·다른 담당 산출물을 정리하지 않는다.
6. 필요한 독립 변경부터 진행하고, 기능별 자기 변경만 커밋·푸시한다. 테스트 전용 작업의 게시 예외는 AGENTS.md를 따른다.

현재 완료 범위는 **이 설계 문서 작성**이다. M0~M5의 게임 구현·게임 빌드·실행 검증은 아직 수행하지 않았다.
