# 첫 성장 구간 장비의 GAS 기여

상태: **정상 모듈 포함과 서버 native의 승인 스킬 query/GE/ExecCalc→실제 HP 피해 통합 확인 완료.** 최신 정상 사본의 피해/수명2개는 Success/오류0·기존 에셋 경고139개이며 무경고 기준은 미달이다. 앞선 독립 모듈의7개 기능 성공/엄격한 실패 기록은 그대로 보존한다. 실제 네트워크 전투·물리 입력 확인은 후속이다.

## 수치와 적용 대상

장비7종의 정확한 Definition ID/Version1·슬롯9/1/4와 명시된 `FirstSlice/1/+0~+3`을 해석한다. 기존 backend의 `FirstSliceEquipmentProgression.Contribution`과 같은 고정 수치다.

| 부위 | 시작 장비 +0 | 목표 장비 +0 | 단계당 추가 |
|---|---:|---:|---:|
| 대검 | 공격력0 | 공격력10 | 공격력3 |
| 상의 | 최대 체력0 | 최대 체력100 | 최대 체력40 |
| 장갑 | 공격력0 | 공격력4 | 공격력2 |

미설정 상태는 기여0이며 옛 아이템에 단계를 채우지 않는다. 명시 상태가 있으나 정의/버전·부위가 지원되지 않으면 적용을 거절한다. 가방/우편·비활성 Record는 기존 장비 Reconcile에서 제외한다. 첫 구간 대검은 주 무기 우측 슬롯에만 있으며 보조 무기/맨손/유틸리티 상태에서는 주 무기의 공격력을 적용하지 않는다. 방어구 기여는 유지한다.

## 권위 장비 복원과 수명

기존 `URPGAuthoritativeEquipmentComponent::Reconcile`의 서버/캐릭터 소유·정의/슬롯·중복 검사를 유지한다. 전체 대상의 성장 정책과 필요한 ASC/Attribute를 먼저 확인하고, 실제 장착 장비의 합계만 native infinite GE 하나로 적용한다. 같은 합계의 반복 복원은 활성 효과가 남아 있으면 재적용하지 않는다. 같은 ItemId/새 단계도 다시 계산하며, 합계 교체·해제·소유 캐릭터 변경·EndPlay 때 이전 효과를 회수한다. 외부에서 효과가 제거된 경우 다음 Reconcile은 다시 적용한다.

Attack/MaxHealth의 base 값을 덮지 않고 additive 기여를 별도로 소유한다. 기존 StatValues·정의 AbilitySet·액터 생성/회수는 유지하며, 기여 계산값을 영속 Record에 다시 쓰지 않는다. 새 RPC/저장 명령·클라이언트 능력치 입력·태그 INI/에셋 변경도 없다. 실제 공격 계산은 기존 GAS Attack Attribute 소비 경로를 그대로 사용한다.

장비로 최대 체력이 늘어도 현재 체력을 채우지 않는다. 상의 교체는 최종 aggregate를 교체한 뒤 현재 체력을 최종 최대치까지만 낮춰, 중간의 미장착 base 최대치로 잘못 자르지 않는다. 현재 체력0은 그대로이며 장비 복원이 부활/시도 초기 회복을 대신하지 않는다.

## 검사와 인계

진행 중인 다른 담당의 성장4명령·journal/전송/UI 경계와 공유 파일을 나눴다. 본인 수정은 규칙 h/cpp·GE h/cpp·기존 권위 장비 h/cpp·집중 native 사례 cpp의7파일이다. 다른 담당의 HttpWebManager/신규 명령 타입·codec·journal/subsystem 및 기존 장비 계약21절은 수정하지 않았다.

검사는 닫힌 Source/Config/Plugin/Binaries 사본과 별도 UHT/UBT/Intermediate/실행 경로를 사용한다. 그 사본에서는 다른 담당이 작성 중인 새 EquipmentMutation 파일/전송 cpp/벡터를 제외하고 기존 HttpWebManager.h의 미참조 helper 선언은 그대로 두었다. 원본에서 이 파일들을 제거하거나 수정한 것은 아니다. 이 결과를 다른 담당의 명령 구현에 대한 검사로 해석하지 않는다.

닫힌 입력1427개에서 독립 UHT/657개 빌드 작업·링크를 완료했다. 종료0·기존 C4996 경고5개이며 본인 추가 코드의 컴파일 오류는 없다. 실제 사설 모듈 `916BA76E…4537EE52`의 로드 경로/해시를 관측하고 native 프로세스 종료0을 확인했다.

- `Recipes`: 7종×4단계의 공격력/체력과 누락 상태0·미지원 정의/버전·슬롯·단계 거절을 확인했다.
- `GasLifecycle`: 실제 설치 정의/ASC를 사용해 목표 +0의 공격력+14/최대 체력+100, 같은 ID의 +3 갱신 +29/+220, 반복 복원의 GE1개 유지·주/보조 전환을 확인했다. 상의 교체 시 최종 상한320·해제 시200으로만 현재 체력을 낮추고, 최대치 증가 시 회복 없음/현재 체력0 유지·전체 해제 후 base 복원을 확인했다.
- `ScopeAndAuthority`: 가방/누락 상태의 무기여, 소유 캐릭터 전환의 이전 기여 회수, 클라이언트 적용 거절을 확인했다. 기존 스냅샷/Ability/추적4개도 모두 Success다.

첫 `GasLifecycle`의 정의 캐시 로드에서 기존 예제/ApexDestruction/애니메이션 에셋 경고139개, 기존 스냅샷 사례의 무기 등록/옛 명령 로그 경고4개가 발생했다. 실행기는 경고가 하나라도 있으면 실패하는 기준이어서 **엄격한 결과는 false**다. 별도 감사에서 정확한7개 사례의 Success/오류0과 실제 값을 확인했으며 원래 결과를 true로 고치거나 경고를 숨기지 않았다. 발견 전 기동 Error15/발견 이후 Error0, 모든 경고의 고유 문구/개수는 `WarningInventory.json`에 보존했다. 제품/사례를 바꾸거나 경고를 없애기 위한 반복 빌드·검사를 하지 않았다.

근거는 [ImplementationResult.json](../Saved/BuildChecks/EquipmentGrowthGas-20261101/ImplementationResult.json)과 연결된 엄격한 원본 Result·Build/Native 로그, 입력/소스 해시·실제 모듈 관측이다. 본인7파일은 컴파일 사본과 최종 원본 해시가 같고, 사본 취득 뒤 관측한 원본 입력 변경도0이다. 다른 담당의 제외 파일/전송 구현을 검증한 결과는 아니다.

자기 프로세스 종료/사용 해제 후 사설 UHT/obj/PCH·DLL/PDB/실행/캐시 **5,180,636,365 bytes(4.825GiB)**·파일5188개/디렉터리544개를 폐기하고 소유 junction11개를 대상 추적 없이 해제했다. Temp/자기 빌드·native 잔여와 정리 예외0이며 폐기 모듈 해시는 당시 증거만 남긴다. 원본 Source7/작은 명령·로그/해시는 유지하고 본인 예약을 해제했다.

다음은 다른 담당의 성장 명령 Source12 작성/고정 입력 인계 후 같은7개 소스 해시를 확인해 정상 모듈에 순차 반영하는 단계다. 이번 private 모듈은 그 작성 중 파일을 제외했으므로 원본 정상 DLL로 복사하지 않았다. 정상 설치·실제 HTTP/PG 왕복/네트워크 피해·복제·픽셀 표시와 무기 고정 효과(보호막/투지)는 별도다. 장비 복원을 전투 시도 시작의 회복으로 취급하지 않는다.

## 2026-11-02 정상 모듈과 승인 피해의 통합 확인

위 정상 반영 대기는 이 후속으로 해소됐다. 다른 담당의 정상 빌드 F2DE4FC3 입력1360개에서 기존 GAS7개 해시가 사설 검증 소스와 일치함을 확인했다. 실제 피해를 검사하는 native 사례1개만 추가하고 정상4작업(CPP1/링크2/metadata1)·종료0/경고0·입력1361개 불변의 E0C8E8CA 모듈을 만들었다. GAS 제품7개·전송 담당 Source12·로비4·에셋/backend/DB는 수정하지 않았다.

정상 출력의 빌드 예약은 다른 담당의 Codec 보완과 갱신 시점이 겹쳤다. 본인 빌드가 종료하고 입력 변경0·실행 중 UBT0을 확인한 즉시 공유 Source/Plugin 읽기·UHT/UBT/Intermediate/정상 출력 예약을 해제했다. 다른 담당의 예약이나 실패 보고서를 바꾸지 않았고 추가 제품 빌드는 하지 않았다. 최종 정상235068FD…ABBD6B10은 그 담당의 파일집합/SHA1361개 불변·성공 근거에서 본인8개(GAS7/피해 사례1)의 동일 해시를 다시 대조해 재사용했다.

검사 과정은 세 번의 결과를 구분한다.

1. 첫 native 실행은 사본에 Content 연결이 빠져 장비 정의를 찾지 못했다. 정상 빌드는 성공했지만 피해/수명 사례는 실패했으며 그 결과를 보존했다.
2. 사본 구성만 보완한 두 번째 준비는 다른 정상 DLL 쓰기와 겹쳐 공유 파일 읽기가 거절됐다. native 기동 전 중단/자동 정리했다.
