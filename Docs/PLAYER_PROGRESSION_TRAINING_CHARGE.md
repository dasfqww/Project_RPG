# 첫 훈련의 기본 차지와 완충 해제 관찰

작성일: 2026-10-30

상태: 코드 수정·분리 native 2개 통과. 훈련 목표의 GAS/네트워크 실제 실행은 별도다.

## 기본 차지가 목표로 인정되지 않던 조건

`URPGSkillDefinition_Charge::ApplyDefinitionExecutionDefaults`는 기본 차지를 부분 충전도 해제할 수 있는 설정으로 만든다. `FRPGSkillChargeExecutionConfig::MinimumReleaseLevel`의 기본값은 0이다. 완충/빠른 충전 트라이포드는 4레벨에서 해제 하한을 최대 단계와 같게 설정한다.

기존 훈련 관찰기는 커밋 당시 `MinimumReleaseLevel == MaxChargeLevel`을 요구했다. 새 캐릭터의 기본 차지는 실제로 끝까지 충전해도 이 검사에서 제외된다. 훈련 전에 4레벨 선택을 요구하거나, 기본 스킬의 부분 충전을 금지하는 방식으로 해결하지 않는다.

## 실제 시전의 해제 결과를 읽는 경계

- `URPGSkillExecutionPolicy_Charge`는 해제 시점의 실제 단계가 최대인지 기존 플래그에 보관한다. 타이머 갱신 사이에 최대 단계에 도달해 해제해도 해제 경로가 직접 계산한다. 단순히 최대 단계까지 기다린 것과 실제 해제를 구분한다.
- 기존 `WasReleasedAtMaximumCharge()`가 이 해제 사실을 읽는다. Ability가 정책을 종료하고 RuntimeSpec을 지운 뒤에도 설정을 다시 읽지 않는다. 새로운 시도나 실패한 재시작은 이전 결과를 초기화한다. 새 복제 필드·RPC·UCLASS/가상 함수·클래스 크기 변경은 없다.
- 공통 SkillContainer에는 현재 시전 정책의 const 조회만 추가했다. 훈련 관찰기는 커밋 당시 해당 차지 정책을 약참조로 기록하고, 같은 활성화의 GAS 정상 종료에서 실제 완충 해제를 확인한다. 부분 충전을 허용하는 기본 설정도 관찰할 수 있다.
- 기존 취소·부여 소유권·활성화 번호·현재 Pawn/인증/복원 수명 검사는 유지한다. 완충 해제 뒤 타깃 실패 등으로 취소된 경우에도 해제 사실 자체는 참일 수 있으므로, 그 사실만으로 목표 완료나 피해 성공을 판정하지 않는다.

훈련 목표 h/cpp는 다른 담당의 에셋 작성 보존 입력이었다. 2026-10-30의 완료·인계/예약 해제와 넘겨받은 소스 해시 일치를 확인한 뒤 수정했다. 작성된 훈련 맵/Pawn/GameMode/서버/보상 에셋과 PlayerUI API는 편집하지 않았다.

## 검증과 적용 범위

집중 검사 `DefaultReleaseAndReset`, `CancellationReuseAndValidation`은 실제 차지 정책과 독립 월드의 시간/타이머를 사용한다. Host의 몽타주·타깃 서비스는 작은 모형이다. 기본 부분 해제와 완충 해제, 타이머 갱신 사이의 해제, 설정 초기화 후 조회, 최대 대기/취소와 무효 재시작을 확인한다. 기존 훈련 컴포넌트의 반영 클래스 할당 크기도 비교한다.

이 검사는 실제 GAS 인증/부여·입력·몽타주·목표 완료의 전체 경로가 아니다. 훈련 맵에서의 기본 공격/회피/돌진/완충 완료, OwnerOnly 전송·가이드, 파티 집계/경험치 정산은 별도로 확인해야 한다. 공유 모듈에는 아직 적용하지 않았다.

분리 검증 기록은 `Saved/BuildChecks/TrainingChargeRelease-20261030/`에 남긴다. 원본 링크 입력의 공용 PlayerUI 객체 누락을 확인해, 완료된 SingleFile 객체와 자체 생성 묶음·로비/결과 객체를 맞추는 독립 스냅샷을 사용한다. 다른 담당이 새 진행 위젯을 구현하고 있어 그 미구현 타입 등록과 미빌드의 무관 테스트는 자체 링크에서 제외하며 전체 현재 타깃 성공으로 계산하지 않는다. 공유 UHT/UBT/Intermediate·원본 DLL은 쓰지 않는다.

성공/실패 모두 임시 입력 사본·OBJ/DLL/PDB·RuntimeProject/UserDir를 finally에서 폐기하고 작은 결과·명령·소스/모듈 해시·필요 로그만 남긴다. 해시가 남아 있어도 폐기한 바이너리의 재실행을 지원한다는 뜻은 아니다.

### 최종 결과

`Saved/BuildChecks/TrainingChargeRelease-20261030/ImplementationResult.json`과 실제 실행 `Saved/Tests/TrainingGuideAutomation/75cbc356cc4a4b969f42965aa92fae49/Verification.proof.json`이 근거다. **CL 9개·분리 링크·native 2개 Success·UE/호스트 종료 0**이다. 자체 정책/목표/검사 CPP 3개 외 6개는 기존 생성 묶음·로비/결과 객체의 기준을 맞추는 컴파일이며 해당 UI 소스는 수정하지 않았다. 링크 사본 452개와 선택 소스 6개/보존 6개를 확인했고 기동 Error 15줄/탐색 이후 0을 구분했다. 정상 공유 모듈은 교체하지 않았다.

초기 원본 객체 누락, PCH가 가리던 패키지 헤더 누락과 분리 컴파일 레시피 문제를 보존했다. 첫 native에서 기본 해제/설정 초기화 사례는 Success였고 최대 대기 사례는 시험용 월드의 타이머 등록/같은 프레임 갱신 가정 때문에 Fail이었다. 제품 코드 그대로 시험 월드의 초기 tick/프레임 진행을 바로잡은 최종 DLL에서 두 사례 모두 Success로 확인했다. 이전 실패를 삭제하거나 성공으로 합산하지 않았다.

러너의 `-ChargeReleaseOnly`가 이 두 검사만 선택하며 기본 뷰포트 검사/`-All` 동작은 유지한다. `-All`과 혼용은 UE/임시 폴더 생성 전에 거절함을 확인했다. 이번 성공/실패의 Temp·실행 사본과 이전 보류 RuntimeProject 210,433,793 bytes를 포함해 **임시 파일 누적 약 8.87GiB를 폐기**, 잔여 대형 예외는 없다. 필요 로그만 추려 원본 로그 해시와 함께 남겼다. 결과 집계 도구가 셸 메타데이터까지 직렬화하던 별도 실행은 소유를 확인해 중단하고 작은 JSON 집계로 보완했으며 게임 검사 프로세스는 방해하지 않았다.
