# 시나리오·퀘스트·대화 JSON 저작

현재 서버 매니저와 로비 이야기 창이 사용하는 정의를 외부 JSON 파일로 작성한다. 파일을 바꾼 뒤 서버를 재시작하면 적용되며, 외부 파일 때문에 게임/서버 코드를 다시 컴파일할 필요는 없다. 실행 중인 카탈로그는 불변이며 자동 감시·부분 교체는 하지 않는다.

이 형식은 개인 대화로 수락 → 작성된 목표를 각각 확인 → 보고하는 의뢰, 서버 클리어 기록의 던전 목표, 승인된 개인 조사/상호작용 사건, 개인 처치 횟수 목표, 완료 의뢰에 따른 챕터/이야기 해금, 진도를 바꾸지 않는 정보형 대화 분기와 명시 챕터의 이야기 스킵을 지원한다. UE 이야기 창에서 스킵 미리보기와 개인 확인을 제공한다. UE 처치 연결은 아래의 명시 저작 옵션을 제공하며 프로젝트 전체 참여 정책·실제 맵 배치/다인 검증과 지역 사건, 보상 지급은 후속 단위다. 아래 SAMPLE은 기술 예시이며 실제 세계관·출시 퀘스트 채택을 뜻하지 않는다.

## 메인·선택 서브 의뢰 분류

퀘스트 정의의 선택 필드 `category`는 `"Main"`, `"Side"`, `"Unspecified"` 중 하나다. 생략하면 기존 미분류 의뢰로 읽으며 ID·제목으로 종류를 추정하지 않는다. 숫자·null·알 수 없는 값은 저작 오류다. 예: `{ "id":"SAMPLE.Main", "version":1, "prerequisites":[], "objectives":["talk"], "category":"Main" }`. 대화의 수락/목표/보고 진입점은 기존 방식으로 함께 작성한다.

`Main` 의뢰는 선행 그래프 어디에도 `Side`를 요구할 수 없다. 중간에 미분류 의뢰나 다른 메인이 있어도 같은 검사다. 이야기 챕터의 `requiredQuests`와 그 선행 그래프도 `Side`를 요구할 수 없다. 선택 서브가 필수 해금·챕터 스킵 자격의 조건이 되는 것을 막으며, 서브가 메인 이후에 열리는 구성은 허용한다. 서브를 챕터 필수 목록에 넣지 않고 독립 의뢰로 작성한다. 잘못된 정의는 서버 시작/오프라인 검사에서 거절하고 저장 진도를 초기화하지 않는다.

저널은 `[메인 의뢰]`, `[선택 서브 의뢰]`와 기존 제목·진행 상태·목표 수량을 함께 표시한다. 미분류 의뢰의 표시는 기존과 같다. 분류는 카탈로그의 표시·선행 검사용이며 기존 개인 기록/명령 영수증 형식, 보상·성장·훈련·스킵 정책을 바꾸지 않는다. 기본 개발 콘텐츠와 실제 첫 챕터를 자동 분류하거나 채택하지 않는다.

## 던전 클리어 목표

퀘스트의 `objectives`에 목표 ID를 넣고 `dungeonObjectives`에서 정확한 던전 ID와 난이도(`Easy`/`Normal`/`Hard`/`Hell`)를 지정한다. 서버 기동 시 선택된 `DungeonContent`에 실제 있는 던전/난이도인지도 검사한다. 카탈로그 단독 검사 CLI는 던전 설정을 읽지 않으므로 형식·내부 참조까지만 확인한다. ID별 한 번의 성공을 인정한다. 반복 횟수나 난이도 이상 판정은 아직 지원하지 않는다.

```json
{
  "id": "SAMPLE.Clear", "version": 1, "prerequisites": [],
  "objectives": ["prepare", "clear"],
  "objectivePrerequisites": { "clear": ["prepare"] },
  "dungeonObjectives": { "clear": { "dungeonId": "sample_dungeon", "difficulty": "Normal" } }
}
```

수락·보고 대화와 `prepare`의 `RecordObjective` 대화를 별도로 작성한다. `clear`에는 `RecordObjective` 선택지를 작성할 수 없다. 서버가 받아 저장한 정산 기록의 확정 수령 대상에 해당 캐릭터가 있어야 하며, 목표가 활성화된 이후의 클리어만 인정한다. 정산 재화/물품의 전달 실패나 재시도는 새로운 클리어가 아니다. 같은 퀘스트의 다른 던전 목표에는 같은 시도 ID를 재사용할 수 없다. 독립된 퀘스트는 각각 수락·선행 조건을 충족하면 같은 사건을 인정할 수 있다.

기존 배포 퀘스트의 목표 종류·선행 조건을 바꿀 때는 정의 버전과 저장 진도의 이행을 함께 설계한다. 이미 저장된 대화 목표를 같은 버전으로 던전 목표로 바꾸면 새 증거 메타데이터가 없어 호환 검사에서 거절한다. 이 기능은 콘텐츠를 자동 추가하거나 기존 의뢰의 의미를 바꾸지 않는다. API와 UE 연결 범위는 [런타임 문서](NARRATIVE_RUNTIME.md#던전-클리어-증거-반영)에 기록한다.

## 계정 완료 이력과 스킵 선행 조회

계정 이력은 별도 저작 파일이나 수동 계정 플래그로 만들지 않는다. 기존 챕터의 `requiredQuests`를 모두 직접 보고 완료한 캐릭터의 저장을 검증하여 산출한다. 필수 의뢰가 `ReadyToReport`인 상태는 이력에 포함되지 않는다. 동일 계정의 여러 캐릭터가 완료한 챕터는 합쳐서 한 번 표시하며 현재 선택 캐릭터의 완료 여부를 따로 제공한다. [조회 API/권위 경계](NARRATIVE_RUNTIME.md#계정의-직접-완료-챕터-이력)를 따른다.

챕터 정의에 선택형 `title`을 작성하면 완료 이력 패널의 표시 이름으로 전달한다. null/생략은 기존 챕터와 호환되며, 지정할 때는 비공백1~256자여야 한다. ID·`requiredQuests`·`storyUnlocks`를 이름 변경 용도로 바꾸지 않는다. 제목만의 변경은 진행 버전/저장 이행을 요구하지 않는다. 출시 콘텐츠에는 알아볼 수 있는 제목을 작성한다. 제목이 없는 예전 데이터는 UE에서 ‘제목 없는 이야기’로 표시하고 내부 ID를 이름으로 노출하지 않는다.

UE의 기존 이야기 창 저널 스크롤 하단에서 ‘계정 이야기 완료 이력’을 확인한다. 버튼으로 조회/재조회하고 이 캐릭터와 다른 캐릭터의 완료를 구분한다. 조회 실패를 ‘완료 없음’으로 해석하지 않는다. 이 패널은 스킵 실행을 제공하지 않는다. [UI 수명/조회 계약](NARRATIVE_RUNTIME.md#ue-계정-완료-이력-패널)을 따른다.

이력에 나온 챕터를 부캐의 `completedChapters`/`storyUnlocks`에 복사하거나 의뢰 보고·성장 지급으로 연결하지 않는다. 이력만으로 잠긴 던전 입장을 허용하지 않는다. 2026-11-12 확정된 무료·챕터 단위/의뢰 보상 미지급/기존 훈련 직접 수행 정책은 아래 서버 계약으로 실행한다. 카탈로그와 기존 캐릭터 저장이 맞지 않는 경우 이력 API는 충돌을 반환하므로 콘텐츠 교체 시 해당 캐릭터의 호환·이행을 먼저 확인한다.

## 챕터 이야기 스킵 저작

검토한 챕터에만 `allowStorySkip: true`를 명시한다. 생략하면 false이며 기존/개발 콘텐츠의 실행 자격을 자동으로 넓히지 않는다.

```json
{
  "id": "SAMPLE.Chapter", "title": "이야기 제목",
  "requiredQuests": ["SAMPLE.Main01", "SAMPLE.Main02"],
  "storyUnlocks": ["SAMPLE.Area"], "allowStorySkip": true
}
```

`requiredQuests`는 생략해도 되는 해당 챕터의 메인 이야기 의뢰만 지정한다. 서브/관계 의뢰는 포함하지 않는다. 이 의뢰가 다른 챕터에도 속하면 시작 시 `ambiguous_story_skip_quests`로 거절한다. 챕터 밖의 이야기 선행은 현재 캐릭터가 직접 완료했거나 먼저 스킵한 상태여야 한다. 기존 훈련·스킬/난이도 자격은 성장 시스템의 실제 기록을 그대로 사용한다.

서버는 미수락·진행 중·보고 대기의 남은 의뢰를 별도 스킵 이력으로 종료한다. 이미 직접 완료한 의뢰와 저장된 목표 사실은 유지한다. 새 성장/전투 사실·XP·아이템·서브 완료를 만들지 않는다. 스킵은 다음 의뢰의 이야기 선행만 충족하며, 정보형 대화의 `requiredCompletedQuests`는 계속 실제 완료를 요구한다. 기본 형식에 없는 NPC 이동·개인/공동 분기·컷신을 자동 생성하지 않는다. 그런 기능이 필요한 콘텐츠는 별도 결과/대체 경로를 먼저 작성·구현한 뒤 스킵을 켠다.

실행은 [서버 미리보기/확인·원자 적용 계약](NARRATIVE_RUNTIME.md#챕터-이야기-스킵-서버)과 [UE 미리보기/확인](NARRATIVE_RUNTIME.md#ue-챕터-스킵-미리보기와-확인)을 따른다. 의뢰 ID/버전/선행이나 챕터 해금 변경은 기존 스킵 기록의 정의 해시와 비교하며, 불일치는 초기화 대신 충돌이다. 무관한 카탈로그 버전 증가는 허용한다. UE는 의뢰/챕터 제목과 해금 개수를 표시하며 논리 ID나 새 NPC 이동/분기 결과를 임의로 화면 이름으로 만들지 않는다. `allowStorySkip` 활성화와 실제 콘텐츠의 해금/성장/대체 경로 검토는 계속 저자의 책임이다.

## UE 적 처치 사건 저작

1. 적 `ARPGNonPlayerCharacter` Blueprint에 `RPGNarrativeKillComponent`를 하나 추가한다. `EnemyId`는 백엔드 처치 목표의 `enemyId`와 정확히 같은 논리 ID로 작성한다. Actor 이름이나 클라이언트가 보낸 문자열로 대체하지 않는다.
2. 인정 방식을 콘텐츠에서 선택할 때 `CreditPolicy = ConfirmedMembersInRadius`, `CreditRadius = 100~100000` UE 단위를 명시한다. 기본값 `Disabled`는 처치 사건을 보내지 않는다. 이 방식은 같은 확정 던전의 적대 팀 멤버가 사망 순간 반경에 있는지를 서버에서 판정한다. 피해/지원·막타/시야 방식으로 읽지 않는다.
3. NPC 시작 데이터가 정상 완료되고 양수 HP였던 실제 생명만 대상이다. HP 0과 서버 사망 태그를 통해 한 번 인정한다. Destroy·웨이브 정리·태그만 붙은 연출·초기 HP 0을 처치로 사용하지 않는다. 재도전은 새 Actor를 생성하며 한 Actor의 태그를 제거하여 새 생명을 흉내 내지 않는다.
4. 퀘스트 수락과 선행 목표, 던전/난이도/적 ID·요구 횟수는 기존 백엔드 정의가 판단한다. 클라이언트에서 횟수를 올리거나 사망 알림만으로 보고/보상을 실행하지 않는다. NPC에 이 컴포넌트를 붙였다는 사실만으로 맵 배치·실제 다인 전송 검증이 완료된 것은 아니다.

프로젝트 전체 처치 인정 정책은 아직 선택 전이다. 반경 방식은 명시 저작 옵션만 제공하며 연결이 끊긴 멤버의 과거 참여·피해 또는 지원 기록을 만들지 않는다. 기본 맵/에셋에는 이 컴포넌트를 자동 추가하지 않는다. 수명·재시도·소유자 재조회는 [런타임 계약](NARRATIVE_RUNTIME.md#ue-사망-사건과-개인-진도-갱신)을 따른다.

## 개인 처치 횟수 목표

`killObjectives`는 던전·난이도·적의 논리 ID와 필요한 횟수를 정의한다. `enemyId`는 서버 콘텐츠 키이며 클라이언트가 제출하는 액터 이름/적 수가 아니다.

```json
{
  "id": "SAMPLE.Hunt", "version": 1, "prerequisites": [],
  "objectives": ["wolves", "leader"],
  "objectivePrerequisites": { "leader": ["wolves"] },
  "killObjectives": {
    "wolves": { "dungeonId": "sample_dungeon", "difficulty": "Normal", "enemyId": "Enemy.Wolf", "requiredCount": 3 },
    "leader": { "dungeonId": "sample_dungeon", "difficulty": "Normal", "enemyId": "Enemy.WolfLeader", "requiredCount": 1 }
  }
}
```

`requiredCount`는 정수1~10000이며 전체 카탈로그의 처치 목표는 최대256개다. 정의된 목표 ID에만 붙일 수 있고 같은 ID를 던전/조사 목표로 중복 지정하거나 `RecordObjective` 대화 선택지로 달성시키면 사전 검사에서 거절한다. 일반 서버 시작 시 던전·난이도 참조도 검사한다. 수락·보고 대화는 별도로 작성한다.

수락 및 선행 목표 완료 후 활성화한 시각 이후의 승인된 처치만 센다. 사건 하나는 1회를 더하며, 같은 순간 조건을 만족한 여러 개인 의뢰/병렬 목표에 반영할 수 있다. 마지막 늑대 처치가 다음 단계의 적 조건까지 만족하더라도 다음 단계는 새 사건을 요구한다. 달성한 목표는 추가 누적하지 않는다. 보고·보상·성장 지급은 처치 사건의 효과가 아니다.

저널 GET의 목표별 `currentCount`/`requiredCount`는 처치 목표의 누적값이다. 나머지 목표에는 null이며 기존 `completed`를 유지한다. 진행 저장은 활성화 시 필요한 횟수를 고정하므로 정의와 불일치하면 호환 충돌로 거절한다. 기존 목표의 횟수·유형·의미를 운영 중 변경할 때는 정의 버전과 저장 이행을 함께 준비한다. UE 저널은 처치 목표에 ‘늑대 처치 (1/3)’처럼 수량을 표시하며 기존 대화/던전/조사 목표는 완료 표식을 유지한다. 실제 사망 사건/대상 선정·전송은 위 UE 적 처치 사건 저작 절을 따르며 전체 참여 정책과 맵/다인 검증은 후속이다.

## 개인 조사·상호작용 목표

서버가 승인한 개인 조사/조작 완료를 `interactionObjectives`로 정의한다. 던전·난이도·논리 대상 ID를 정확히 지정한다. 대상 ID는 서버의 현장 액터/기믹과 공유할 저작 키이며 클라이언트가 고르는 완료 버튼 ID가 아니다.

UE 맵에는 `ARPGNarrativeInvestigation`을 배치하고 `TargetId`를 아래 목표의 `targetId`와 정확히 맞춘다. `DisplayName`, 선택 `Appearance` 메시, 거리(50~1000cm, 기본250cm)를 설정한다. 액터의 QueryOnly/WorldDynamic 조사 영역을 기존 상호작용 탐색에 유지하고, 가림막은 Visibility를 차단하도록 저작한다. 이 액터는 즉시 조사이며 `InteractionDuration`은 BeginPlay에서0으로 고정한다. 길게 누르는 작업·아이템 소비는 추가 계약이 필요하다. 논리 대상 ID가 같으면 같은 종류의 조사로 인정하므로 서로 다른 유물을 구분하려면 서로 다른 키를 사용한다. 런타임에 소환하더라도 논리 대상 ID는 서버에서 읽으며 클라이언트 RPC 인자로 받지 않는다.

입력은 기존 `ARPGPlayerController`의 상호작용과 기본 `URPGNarrativeInvestigationComponent`를 사용한다. 클라이언트는 액터 참조와 입력 상관 ID만 보내며 서버가 실제 `TargetId`, 생존 Pawn, 최종 입장 확인, 개인 인증/접속 세대, 거리/시야를 확인한다. 다른 캐릭터의 진도나 파티 전체 사건을 대신 기록하지 않는다. 미수락 상태의 조사도 무효과 영수증으로 확정되므로 수락 후 새로 조사해야 한다. 순차 목표의 다음 단계 역시 새 입력·새 사건을 요구한다.

```json
{
  "id": "SAMPLE.Inspect", "version": 1, "prerequisites": [],
  "objectives": ["briefing", "inspect"],
  "objectivePrerequisites": { "inspect": ["briefing"] },
  "interactionObjectives": {
    "inspect": { "dungeonId": "sample_dungeon", "difficulty": "Normal", "targetId": "Scene.Seal01" }
  }
}
```

수락·보고와 `briefing`의 대화 선택지를 별도로 작성한다. `inspect`에 `RecordObjective` 선택지를 추가하거나 같은 목표 ID를 던전 결과 목표와 중복 정의하면 사전 검사에서 거절한다. 전체 카탈로그의 상호작용 목표는 최대 256개이며 서버 기동 시 던전/난이도 참조를 검사한다. 기존 배포 퀘스트의 유형을 변경할 때는 정의 버전과 저장 이행을 함께 설계한다.

목표 활성화 이후 발생한 사건만 인정한다. 같은 대상이라도 선행 목표가 끝나기 전에 발생한 사건을 다음 단계로 소급하지 않는다. 한 사건은 그 순간 조건이 맞는 여러 개인 의뢰/병렬 목표에 반영할 수 있으나 같은 사건으로 순차 단계를 연달아 달성하지 않는다. 실제 보고는 별도다. 수량 누적, 아이템 소비, 파티 전체 참여 판정과 전파는 이 유형에 포함하지 않는다.

서버 처리 경로는 [런타임 계약](NARRATIVE_RUNTIME.md#개인-조사상호작용-서버-사건)을 따른다. UE 현장 액터의 권위 판정·승인 이벤트 전송·화면 갱신 알림 연결은 후속 단위다. 이 저작 형식만으로 기존 `IInteractionInterface` 호출이 서버 사건이 되지는 않는다.

## 파일 선택과 사전 검사

서버 설정 예시:

```json
{
  "Narrative": {
    "CatalogPath": "Content/story.json",
    "EnableDevelopmentContent": false
  }
}
```

상대 경로는 ASP.NET의 `ContentRootPath` 기준이다. 배포 시 파일을 명시한 위치에 함께 설치한다. 배포 작업 디렉터리가 달라질 수 있으면 절대 경로를 사용한다. 운영 파일을 저장소의 개발 예제로 자동 대체하지 않는다.

DB 연결·서비스 시작 없이 검사하려면 다음 명령을 사용한다.

```powershell
dotnet run --project Backend/ProjectRpg.Backend -- --validate-narrative-catalog --Narrative:CatalogPath="C:/RPGContent/story.json"
```

성공하면 카탈로그 버전과 의뢰/챕터/대화 개수를 출력하고 종료0, 실패하면 오류 코드와 가능한 JSON 경로를 반환하며 비정상 종료한다. 검증 모드와 `--migrate-schema`는 동시에 지정할 수 없다. 일반 서버 시작과 마이그레이션 모드에서도 선택한 콘텐츠를 먼저 검증한다.

파일 선택도 개발 플래그도 없으면 기존처럼 빈 카탈로그를 사용한다. 개발 예제는 `EnableDevelopmentContent=true`일 때 Development/Testing에서만 제공한다. 개발 플래그와 파일을 동시에 지정하면 모호한 설정으로 거절한다. `DEV.` 정의/이야기 해금 ID는 개발 예제용 예약 접두사이며 운영 환경의 외부 파일에서도 거절한다. 기존 개발 의뢰의 ID·대사·진도·성장 보상0 계약은 유지한다.

## 최소 작성 예시

```json
{
  "schemaVersion": 1,
  "catalogVersion": 1,
  "quests": [
    {
      "id": "SAMPLE.Intro", "version": 1, "prerequisites": [], "objectives": ["briefing"],
      "title": "안내 확인",
      "objectiveTexts": { "briefing": "연락책에게 안내 듣기" }
    }
  ],
  "chapters": [
    { "id": "SAMPLE.Prologue", "requiredQuests": ["SAMPLE.Intro"], "storyUnlocks": ["SAMPLE.Next"] }
  ],
  "dialogues": [
    {
      "id": "SAMPLE.Offer", "speaker": "연락책", "text": "안내를 확인하시겠습니까?",
      "questId": "SAMPLE.Intro", "requiredStatus": null,
      "choices": [{ "id": "accept", "text": "확인하겠습니다.", "effect": "AcceptQuest" }]
    },
    {
      "id": "SAMPLE.Briefing", "speaker": "연락책", "text": "이 대화는 시스템 연결을 확인하는 예시입니다.",
      "questId": "SAMPLE.Intro", "requiredStatus": "Active",
      "choices": [{ "id": "confirm", "text": "확인했습니다.", "effect": "RecordObjective", "objectiveId": "briefing" }]
    },
    {
      "id": "SAMPLE.Report", "speaker": "연락책", "text": "확인을 마쳤군요.",
      "questId": "SAMPLE.Intro", "requiredStatus": "ReadyToReport",
      "choices": [{ "id": "report", "text": "보고를 마칩니다.", "effect": "ReportQuest" }]
    }
  ]
}
```

## 형식과 연결 규칙

| 요소 | 규칙 |
|---|---|
| 최상위 | `schemaVersion=1`, 양의 정수 `catalogVersion`, 배열 `quests`/`chapters`/`dialogues` 필수 |
| 의뢰 | 양의 정수 `version`, `prerequisites` 배열, 비어 있지 않은 `objectives` 배열. 모든 선행 의뢰를 완료해야 수락 가능 |
| 의뢰 표시 | 선택 사항 `title`과 `objectiveTexts`(목표 ID → 설명). 기존 파일은 생략 가능. 지정한 설명의 키는 해당 의뢰의 목표여야 함 |
| 목표 선행 조건 | 선택 사항 `objectivePrerequisites`(목표 ID → 선행 목표 ID 배열). 같은 의뢰의 선행 목표를 모두 확인한 뒤 진행 가능 |
| 챕터 | 비어 있지 않은 `requiredQuests`, `storyUnlocks` 배열. 필수 의뢰 전부 완료 시 계산 |
| 대화 | ID·화자·본문·대상 의뢰·`requiredStatus`·선택지 필수. 새 의뢰 제안의 상태도 생략하지 않고 명시적 `null` 사용 |
| 수락 | `effect=AcceptQuest`, 대화의 `requiredStatus=null`, `objectiveId` 없음 |
| 목표 확인 | `effect=RecordObjective`, 대화의 `requiredStatus=Active`, 해당 의뢰에 작성한 `objectiveId` 필수 |
| 보고 | `effect=ReportQuest`, 대화의 `requiredStatus=ReadyToReport`, `objectiveId` 없음 |
| 정보형 대화 | 노드의 `informational=true`, `questId=null`, `requiredStatus=null`. 선택지는 `effect=None`, `objectiveId` 없음 |

모든 목표는 한 번씩 확인하는 AND 목표다. 완료한 목표의 선택지는 다시 노출하지 않으며, 전부 확인하면 보고 가능 상태가 된다. 의뢰마다 수락·보고와 모든 목표를 기록할 수 있는 대화 경로가 있어야 한다. 선행 참조 누락·자기 참조/순환·정의/선택지/목표 중복을 거절한다. 상태와 효과의 조합도 검사한다.

ID는 영문 ASCII 문자·숫자·마침표·밑줄·하이픈만 사용하며 최대128자다. 화자·본문·선택지 문장은 ID와 분리된 UTF-8 텍스트다. 문장의 변경이 영속 ID를 바꾸는 이유가 되지 않는다.

| 현재 UE 계약에 맞춘 상한 | 값 |
|---|---|
| UTF-8 파일 | 1MiB, BOM 허용, JSON 깊이16 |
| 의뢰/챕터/대화 정의 | 각각256개 |
| 의뢰별 목표·선행 / 전체 고유 이야기 해금 | 각각256개 |
| 대화별 선택지 | 64개 |
| 화자 / 본문 / 선택지 문장 | 각각256 / 4096 / 1024 UTF-16 코드 단위 |
| 의뢰명 / 목표 설명 | 각각256 / 1024 UTF-16 코드 단위. 지정한 값은 공백만으로 작성할 수 없음 |

모든 노드·선택지·진도 ID를 포함한 응답 크기를 과대 추정해, JSON 이스케이프 후에도 UE의 1MiB 응답 한도를 넘지 않는지 검사한다. 이 상한은 이번 첫 클라이언트 계약의 한도이며 대형 카탈로그 분할·페이지 조회를 구현했다는 뜻은 아니다.

누락된 필수 속성, 알 수 없는 속성·상태·효과, 숫자로 쓴 enum, JSON 속성 중복, 잘못된 참조는 거절한다. 예를 들어 `xp`, `itemReward`, `GrantXp`를 작성해도 보상 효과가 추가되지 않는다. 세 진행 효과와 정보형 대화의 `None` 외의 효과는 별도 서버 계약과 구현이 필요하다.

## 순차 목표와 동시 목표

의뢰의 선택 사항 `objectivePrerequisites`에 다음 목표를 진행하기 전에 확인할 목표를 작성한다. 다음 예시는 같은 의뢰에 `contact`와 `preparation` 목표가 있을 때 사용한다.

```json
{ "objectivePrerequisites": { "preparation": ["contact"] } }
```

예시에서는 `contact`를 확인한 뒤 `preparation`을 확인할 수 있다. 필드를 생략하거나 null/빈 객체로 두면 기존처럼 모든 목표를 동시에 진행할 수 있다. 목록에 없는 목표와 빈 선행 배열을 가진 목표에도 추가 조건이 없다. 여러 선행 목표를 나열하면 전부 확인해야 하므로 동시 목표들이 한 후속 목표로 합류하거나 여러 단계를 이어가는 구성을 작성할 수 있다. 의뢰 완료 자체는 기존처럼 모든 목표를 확인한 뒤 보고하는 방식이다.

키와 선행 ID는 모두 해당 의뢰의 `objectives`에 있어야 한다. 목표별 선행 배열은 null을 허용하지 않으며 최대256개, 중복·자기 참조·순환을 거절한다. 의뢰 사이의 선행은 기존 `prerequisites`로 작성한다. 준비되지 않은 목표의 선택지는 조회 응답에서 제외하고, 가능한 선택지가 없는 대화 노드도 제외한다. 저널은 기존 전체 목표 목록을 유지하며 선택 가능한 진행 동작만 제한한다.

ID를 직접 제출해도 서버가 선행을 다시 검사한다. 거절된 요청은 목표·리비전·명령 영수증을 만들지 않는다. 완료된 목표는 재전송 영수증 복구와 구분해 중복 확인하지 않는다. 저장에서 선행 없이 후속만 완료된 상태가 발견되면 충돌을 반환하고 초기화·자동 완료하지 않는다. 이미 배포한 목표의 조건 변경은 기존 정의 버전/저장 호환 규칙을 적용하며, 자동 이전 기능을 추가하는 설정이 아니다. 처치·조사·파티 사건의 달성 근거는 별도 서버 사건 연결 대상이다.

## 월드 NPC 대화 진입점

레벨에 `RPGNarrativeNPC` 액터 또는 그 Blueprint를 배치한다. `Appearance`에 표시할 메시, `DisplayName`에 이름, `DialogueEntryIds`에 이 NPC에서 열 대화 진입점 ID를 설정한다. 예를 들어 개발 의뢰의 연락책에는 `DEV.Contact.Offer`, `DEV.Contact.Explain`, `DEV.Contact.Report`를, 교관에는 `DEV.Instructor.Explain`을 지정한다. 개발 ID는 기존 개발 콘텐츠를 켠 전용 서버에서 사용하는 예시다.

기존 Controller의 WorldDynamic 주변 조회와 `IInteractionInterface`가 액터를 찾고 상호작용 입력을 전달한다. NPC는 소유 LocalPlayer의 UIManager로 대화창을 연다. 선택 캐릭터·로그인·거리·월드/소유 Pawn을 확인하고, 서버의 가능한 대화 중 해당 NPC의 진입점만 표시한다. 같은 NPC를 다시 누르면 열린 창을 재사용한다. 메시 충돌과 별개인 `InteractionBounds`를 사용한다. 탐색 범위는 기존 Controller의 주변 조회 설정을 따르며, `InteractionDistance`는 상호작용/열린 창 유지의 최대 거리를 50~1000 범위의 유한 값으로 처리한다. 진입점 목록은 1~256개·ID당128자·중복 없는 ASCII ID 규칙을 따른다. 비정상 목록에서는 상호작용을 시작하지 않는다.

서버가 허용한 정보형 진입점의 다음/뒤로가기 링크는 같은 창에서 탐색한다. 다른 NPC의 진입점이나 다른 창이 연 대화는 이 창의 선택으로 사용할 수 없다. 현재 가능한 선택지가 없으면 빈 상태를 표시하며 저널은 기존 캐릭터 전체 진도를 보여준다. 거리 이탈·NPC 소멸·Pawn 교체/해제·계정/엔드포인트/캐릭터 변경 시 NPC 창과 그 창이 연 로컬 대화를 닫는다.

가방·스킬 창과 같은 `FRPGWindowInputState`를 사용해 마우스 포커스·이동/시선 입력 잠금을 관리하고, Esc 또는 닫기 버튼으로 닫는다. 기존 RPG Controller에서는 SkillWindowComponent의 공유 상태를 사용하며, 그 컴포넌트가 없는 일반 로컬 Controller에는 창 전용 상태를 사용한다. 창이 닫히면 자기 창의 입력 잠금만 해제하고 다른 창/시스템의 잠금과 커서 상태를 보존한다.

닫기는 진행 중인 명령을 취소하거나 저장을 되돌리지 않는다. 결과 미확정 요청은 Coordinator에 보존하며, 같은 NPC의 진입점에 속한 요청이면 NPC를 다시 열어 원래 명령으로 확인한다. 다른 NPC의 대화창에서 그 요청을 재전송하지 않는다. 기존 로비 이야기 창도 동일한 Coordinator의 복구 경로를 계속 제공한다.

이 액터는 정적 레벨에 배치하는 대화 표시·입력 진입점이며 기존 서버 대화의 전역 접근 정책을 사용한다. 선택 자격·퀘스트 전이·해금·저장·중복 방지는 기존 백엔드가 검사한다. NPC 거리 검사는 로컬 창의 수명 조건이고, 서버의 월드 사건/거리 증명이 필요한 조사·전투 목표는 해당 서버 사건 경로에서 별도로 연결한다. 기존 레벨/메시/최종 NPC 콘텐츠는 이 클래스의 저작 설정과 구분한다.

## NPC 개인 의뢰 표식

`ARPGNarrativeNPC`의 `DialogueEntryIds`에 해당 NPC가 제공하는 수락·진행·보고 노드를 함께 지정한다. 기존 서버가 해당 캐릭터에게 현재 허용한 `entryPoint`와 정확히 일치하는 노드만 표식에 참여한다. 새 응답의 `questId`/`questAction`은 서버의 정의·상태에서 계산한 읽기 메타데이터이며 JSON 콘텐츠에 별도로 표식 상태를 작성하거나 플레이어가 선택 명령으로 제출하지 않는다.

한 NPC에 여러 의뢰가 있으면 **보고 가능 → 새 의뢰 → 의뢰 진행 → 대화 가능** 순서로 대표 문구 하나를 표시한다. 문자·내부 ID·선택지 문장으로 상태를 추정하지 않으며 구 서버의 메타데이터 없는 노드는 일반 ‘대화 가능’으로만 표시한다. 현재 허용 노드가 없으면 빈 표식이다. 같은 메시에 대해 각 LocalPlayer의 화면용 `UWidgetComponent`를 따로 만들고 `OwnerPlayer`를 지정하므로 공용 월드 이름표의 개인 진도를 덮어쓰지 않는다.

`bShowPersonalQuestMarker`로 NPC별 표시를 끄고 `QuestMarkerDistance`(기본2000, 유효 범위50~10000)로 표시 거리를 지정한다. 인증/선택 캐릭터·읽을 수 있는 이야기 캐시·현재 Pawn/월드/거리 조건을 만족해야 표시한다. 표식 자체는 HTTP 조회·의뢰 수락/보고를 하지 않는다. 아직 이야기 진도를 읽지 않은 상태는 숨기며, 기존 이야기 창 등에서 정상 조회된 뒤 표시된다. 표식에는 의뢰명·목표·후일담 같은 상세 스포일러 대신 상태 문구만 노출한다. 전용 서버에는 화면 컴포넌트를 만들지 않으며 해당 NPC 종료/로컬 플레이어 제거 때 자기 컴포넌트만 정리한다.

## 정보형 질문·돌아가기·닫기

정보형 노드에는 `informational=true`를 지정하고, `questId`와 `requiredStatus`는 명시적 `null`로 작성한다. 선택지는 `effect=None`을 사용한다. `nextDialogueId`가 있으면 해당 정보형 노드로 이동하고, 없거나 `null`이면 대화를 닫는다. `objectiveId`와 진행 효과를 섞을 수 없다. 기존 진행형 노드는 `informational`을 생략하거나 false로 두며 다음 노드 링크를 가질 수 없다.

`entryPoint`는 기본 true다. 주제 목록에 직접 보여줄 시작 노드만 true로 두고, 이어지는 설명 노드는 false로 작성한다. 새 클라이언트는 시작 노드만 목록에 표시하며 선택지 링크로 설명 노드에 들어간다. 돌아가기는 이전 주제 노드를 가리키는 링크로 작성한다. 정보형 순환은 허용하지만 모든 정보형 노드는 하나 이상의 시작점에서 도달 가능해야 한다. 없는 대상·진행형 대상 링크·고립된 설명 노드는 검사에서 거절한다. 진행형 노드를 숨기는 `entryPoint=false`도 거절한다.

완전한 3노드 작성 예시는 [검증용 정보 대화 파일](../Backend/ProjectRpg.Backend.NarrativeTests/Fixtures/information.json)에 있다. 새 캐릭터용 정보 전용 카탈로그로 읽거나, 운영 중인 정의를 보존한 채 해당 `dialogues` 항목을 기존 카탈로그에 합친다. 기존 캐릭터의 의뢰 정의를 지우면서 이 예제만 배포하면 기존 저장 호환 규칙에 의해 거절될 수 있다.

서버 조회는 소유 캐릭터의 대화 그래프를 반환하고, 질문·뒤로가기·닫기는 그 스냅샷 안에서 LocalPlayer의 현재 대화만 바꾼다. 쓰기 요청/명령 ID·영수증을 만들지 않으며 퀘스트 목표·리비전·해금·보상·성장을 변경하지 않는다. 정보 선택을 POST로 위조하면 서버도 `informational_dialogue_not_mutable`로 거절한다. 이 방식은 일반 질문 재열람용이며 영구 분기·관계도 저장·NPC 거리/월드 상호작용 판정을 대신하지 않는다.

## 완료 조건이 있는 안내·후일담

정보형 대화에 선택 사항 `requiredCompletedQuests`를 작성하면, 소유 캐릭터가 지정한 의뢰를 전부 완료한 뒤에만 그 노드가 조회 응답에 포함된다. 생략하거나 빈 배열이면 기존처럼 추가 완료 조건이 없다. 수락·진행 중·보고 가능은 완료로 인정하지 않으며 다른 캐릭터의 완료 이력도 대신 사용하지 않는다.

```json
{ "requiredCompletedQuests": ["SAMPLE.Intro"] }
```

이 필드를 해당 정보 대화의 각 노드에 추가한다. 연결된 노드들은 순서와 무관하게 동일한 조건 집합을 가져야 한다. 조건이 있는 시작점에서 조건 없는 설명으로 연결하는 경우도 거절한다. 따라서 대화 전체가 함께 공개되고, 공개된 링크가 숨겨진 노드로 향하지 않는다. 별도 대화는 서로 다른 조건을 가질 수 있다. 의뢰 참조 누락·중복·잘못된 ID·256개 초과를 검사하며, 진행형 대화에 이 조건을 붙일 수 없다. 의뢰 수락의 선행 조건은 기존 `prerequisites`를 사용한다.

조건 미충족 노드는 진입점/설명/선택지/문구 전체가 응답에서 제외된다. ID를 알고 POST해도 서버가 같은 자격을 재검사해 거절하며 영수증을 만들지 않는다. 공개된 정보 선택도 기존처럼 쓰기로 처리하지 않는다. 이 조건은 표시할 대화의 자격이며 던전 입장 해금이나 보상·성장 지급을 추가하지 않는다. 조건을 바꾸는 배포는 기존 카탈로그 버전/저장 호환 규칙과 클라이언트 재조회를 함께 고려한다.

## 이야기 해금과 던전 입장

던전 운영 설정 `DungeonContent:Entries`의 선택 사항 `RequiredStoryUnlocks`로 해당 던전의 이야기 입장 조건을 지정한다. 값은 이야기 JSON의 챕터 `storyUnlocks`에서 정의한 ID이며, 지정한 조건을 해당 캐릭터가 전부 가지고 있어야 한다. 같은 던전의 모든 등록 난이도에 적용된다. 난이도별 기존 성장·실습 조건은 함께 충족해야 한다.

```json
{
  "DungeonContent": {
    "Entries": [{
      "DungeonId": "Dungeon.Sample",
      "MapPackage": "/Game/Maps/Sample",
      "Difficulties": ["Normal", "Hard"],
      "RequiredStoryUnlocks": ["Story.Sample.Open"]
    }]
  }
}
```

누락·빈 배열은 추가 이야기 조건이 없는 기존 콘텐츠다. null·잘못된 ID·중복·256개 초과는 거절하며, 정의되지 않은 해금 참조도 일반 서버 시작 시 거절한다. 던전 설정과 이야기 정의는 프로세스 수명 동안 고정하고 설정 객체를 나중에 변경해도 검사 조건이 바뀌지 않는다. `--validate-narrative-catalog`는 이야기 파일만 검사하므로 두 설정의 연결 검사는 일반 서버 기동에서 확인한다. 기본 설정에 개발 의뢰나 미승인 첫 챕터를 임의로 연결하지 않는다.

서버는 방 생성·파티 참가·입장권 발급·게임 서버의 최종 입장 승인에서 캐릭터 본인의 저장을 검사한다. 참가 대상 던전은 서버의 세션에서 읽는다. 방장·같은 계정의 다른 캐릭터 완료로 자격을 대체하지 않는다. 조건 부족은 HTTP409 `story_prerequisite_not_met`, 저장 버전/진도/해금이 모순된 경우는 `story_progress_unavailable`이다. 저장을 초기화하거나 해금을 지급하며 통과시키지 않는다.

이미 발급된 입장권도 최종 승인에서 검사하므로 과거 입장권이 자격을 대신하지 않는다. 입장권 소비·영수증 복구는 기존 경로대로 처리하며 소비 성공이 최종 입장 승인을 뜻하지 않는다. 조건을 만족하면 기존 소비 요청과 연결 세대로 승인을 다시 시도할 수 있다. 이 검사는 이야기 진도·명령 영수증·경험치·스킬·보상을 변경하지 않으며 반복 입장에 대화 재수행을 요구하지 않는다. 운영 중 새 조건을 추가할 때는 기존 세션/입장권과 저장 호환성을 함께 검토한다.

## 버전과 기존 저장

`schemaVersion`은 파일 형식 버전, `catalogVersion`은 선택 요청이 바라보는 콘텐츠 묶음 버전, 의뢰의 `version`은 해당 저장 진도의 정의 버전이다. 서버는 선택 요청의 카탈로그 버전과 저장된 의뢰 정의 버전을 대조한다. 기존 ID 삭제·버전 변경·챕터 필수 조건/해금 변경이 기존 저장을 자동 변환하지 않는다. 저장과 맞지 않으면 기존 런타임 계약에 따라 충돌을 반환하며 새 진도로 초기화하지 않는다.

운영 교체 전에는 실제 저장과의 호환 또는 별도 마이그레이션을 검토하고, 사전 검사 후 같은 파일을 모든 해당 서버에 배포한다. 진행 데이터·완료 영수증·성장 상태는 카탈로그 파일에 작성하지 않는다.
