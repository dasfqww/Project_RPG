# 플레이어블 직업 설계 방향

작성일: 2026-10-25

상태: 직업·스킬 구성과 구현 구조의 설계 초안. 합의한 방향과 필수 설계 원칙을 기록하고, 직업별 세부 제안과 남은 결정을 구분한다. 이 문서는 구현 완료 기록이 아니다.

이 문서를 직업 설계와 다음 작업의 시작점으로 사용한다. 1~2절은 합의한 게임 방향, 3~4절은 직업·스킬 후보, 6절은 지금 필요한 기준과 나중에 정할 내용, 8~9절은 구현 구조와 기존 코드 연결의 기준이다. 미정 항목 전체를 확정해야 구현을 시작할 수 있는 것은 아니다.

실제 구현 시에는 현재 소스의 API와 10절에 연결한 스킬·공통 피격 규칙을 필요한 범위에서 확인한다. 문서의 제안이나 과거 코드 조사 결과를 현재 구현 완료 상태로 간주하지 않는다.

## 1. 합의한 방향과 수량 기준

플레이어블 직업은 혼자서도 전투가 성립하고, 파티에서는 서로의 공격 기회와 생존을 돕는 방향으로 설계한다. 특정 탱커나 힐러가 있어야만 공략할 수 있는 파티 구조를 기본으로 삼지 않는다.

| 항목 | 현재 방향 |
|---|---|
| 직업의 기본 역할 | 모든 직업이 독립적으로 공격과 기본 생존을 수행 |
| 직업의 차이 | 공격 기회를 만드는 방법, 거리, 공격 동작의 부담, 자원 운용, 대응 방식 |
| 파티에서의 강점 | 보호, 제어, 무력화, 부위 파괴 등으로 다른 플레이어의 전투를 보조 |
| 선택 가능한 액티브 스킬 | 최종적으로 직업당 12~16개를 기본안으로 설정 |
| 전투에 장착하는 액티브 스킬 | 8개를 기본안으로 설정 |
| 고유 능력 | 직업당 1개를 기본안으로 설정. 장착 스킬 8개와 별도 |
| 기본 공격·회피 | 장착 스킬 수와 별도로 구성 |
| 초기 설계 범위 | 첫 직업의 중심 스킬 몇 개로 출발하고 후보 약 12개까지 점진적으로 확장 |
| 첫 직업 제작 목표 | 최대 8개 편성과 고유 능력으로 전투 구성을 완성. 전체 8개 확정은 구현 착수의 전제조건이 아님 |
| 코드 설계 필수 조건 | SOLID와 책임별 모듈화. 신규 직업 추가가 기존 직업과 공통 캐릭터의 직업별 분기 증가로 이어지지 않도록 설계 |

앞서 논의한 스킬 4개는 각 직업의 중심이 되는 기술이며, 직업의 전투 감각을 먼저 확인하기 위한 수량이다. 완성형 직업의 전체 스킬 수를 4개로 제한하는 뜻이 아니다. 고유 능력도 기본안은 1개지만, 효과·자원·입력 방식은 직업별로 검토한다.

8개는 전투 편성의 최대 슬롯 수다. 성장 초기의 미습득 스킬이나 사용자가 비운 슬롯까지 채우기 위해 스킬을 자동 습득시키지 않는다. 직업별 12~16개 스킬을 언제 습득하는지는 별도 성장 규칙으로 정한다.

## 2. 공통 전투 원칙

- 모든 직업에 기본 회피와 생존 수단을 마련한다. 회복은 우선 공통 회복 수단을 바탕으로 하고 직업별 보조 능력을 제한적으로 더한다.
- 파티 보조는 자신의 공격과 자연스럽게 연결한다. 공격을 거의 포기하고 보호·회복만 담당하는 플레이를 필수 역할로 요구하지 않는다.
- 직업마다 강점과 약점을 남긴다. 긴 공격 동작, 조준 시간, 위치 선정, 자원 부족 등이 실제 판단에 영향을 줘야 한다.
- 무력화·부위 파괴 같은 공통 기믹에 각 직업이 참여할 방법을 둔다. 직업별 기여 방식과 효율에는 차이를 줄 수 있다.
- 특정 직업의 독점 능력을 던전의 필수 해법으로 만들지 않는다. 보호·회복·파티 강화가 지나치게 강해 사실상 필수 직업이 되는지도 검토한다.
- 일반 적에게 적용하는 둔화·속박 등의 제어와 보스의 반응 규칙을 구분한다. 보스에게 어떤 제어가 허용되고 무력화에 어떻게 기여하는지는 공통 피격·상태이상 설계와 맞춘다.

회복량, 포션 제한, 부활 규칙, 보스의 제어 면역과 무력화 수치는 아직 정하지 않았다.

## 3. 초기 직업 후보

다음 4종은 검토할 후보이며, 명칭과 최종 출시 직업 수는 미확정이다.

| 직업 후보 | 핵심 재미 | 파티에서의 강점 | 주요 부담 |
|---|---|---|---|
| 대검 전사 | 적의 빈틈에 강한 공격을 끝까지 성공시키기 | 무력화·부위 파괴, 공격 기회에 집중 피해 | 긴 공격 동작과 접근 위험 |
| 창방패 기사 | 방어와 반격을 공격으로 이어가기 | 짧은 보호, 적의 공격에 대응해 공격 기회 확보 | 방어 여력과 방향 관리 |
| 궁수 | 이동 사격으로 기회를 만들고 정확하게 사격하기 | 지속 압박, 노출된 약점 공략 | 조준 시간과 사격 위치 확보 |
| 원소술사 | 적의 움직임을 예측하고 주문을 조합하기 | 범위 공격과 제어 | 시전 시간, 설치 위치와 적 이동 예측 |

쌍검 암살자와 성직자는 추후 확장 후보로만 남긴다. 성직자를 추가한다면 공격하면서 보호·회복을 제공하는 방향부터 검토한다.

## 4. 직업별 스킬 초안

아래 스킬명과 효과는 제안이다. 확정된 밸런스, 실제 에셋 연결 또는 구현 상태를 의미하지 않는다. 각 직업의 기본 공격·회피는 표에서 생략한다.

### 4.1 대검 전사

묵직한 타격감과 큰 공격을 성공시켰을 때의 보상을 중심으로 한다. 공격을 계속 밀어붙일지, 회피하고 다음 빈틈을 기다릴지 판단하는 직업이다.

| 구분 | 가칭 | 동작과 사용 목적 |
|---|---|---|
| 중심 스킬 | 돌진 베기 | 짧게 돌진하며 베어 접근한다. 이동 수단으로도 활용 |
| 중심 스킬 | 도약 강타 | 가까운 지정 위치에 내려찍는다. 다수전과 부위 파괴에 활용 |
| 중심 스킬 | 차지 슬래시 | 힘을 모아 강하게 내려벤다. 긴 공격 기회에 사용하는 주력기 |
| 중심 스킬 | 회전 베기 | 이동하면서 주변을 연속 공격한다. 다수전과 지속 공격 담당 |
| 고유 능력 | 투지 해방 | 공격으로 쌓은 투지를 소비해 다음 주력기를 강화하는 안 |

투지는 차지 슬래시의 한 방을 강화할지, 회전 베기를 강화해 지속적으로 압박할지 선택하게 하는 방향이다. 투지 획득 조건, 강화 대상과 소모량은 미정이다.

추가로 논의한 스킬 후보는 다음과 같다.

| 가칭 | 기존 중심 스킬과 다른 선택 이유 |
|---|---|
| 빠른 횡베기 | 짧은 빈틈에도 사용할 수 있는 빠른 공격 |
| 반격 베기 | 적의 공격에 대응하면서 공격을 이어가는 선택 |
| 검풍 | 접근하기 어려운 순간에 사용하는 중거리 공격 |

현재 구체적으로 논의한 액티브 후보는 중심 스킬 4개와 추가 후보 3개로 총 7개다. 최초 제작할 8번째 스킬과 약 12개까지의 나머지 후보는 다음 논의에서 정한다.

가능한 빌드 방향은 차지 공격 중심, 빠른 연계 중심, 회전 공격 중심이다. 기존 대검 스킬은 재사용을 검토할 기반이며, 이름이 비슷했던 D1 Whirlwind Slash 등 폐기한 D1 구현과 구분한다.

### 4.2 창방패 기사

가드와 공격이 번갈아 이어지는 재미를 중심으로 한다. 혼자 싸울 때도 찌르기와 반격으로 충분히 공격적인 전투가 성립해야 한다.

| 구분 | 가칭 | 동작과 사용 목적 |
|---|---|---|
| 중심 스킬 | 진격 찌르기 | 방패를 앞세워 전진한 뒤 창으로 찌른다 |
| 중심 스킬 | 받아치기 | 짧은 방어 동작 뒤 반격한다. 타이밍을 맞춰 막으면 반격 강화 |
| 중심 스킬 | 관통 연격 | 전방을 연속으로 찌르는 주력 공격. 방어 뒤 공격을 이어갈 때 활용 |
| 중심 스킬 | 방벽 전개 | 짧은 시간 전방을 보호해 자신과 가까운 아군의 공격 기회를 확보 |
| 고유 능력 | 방패 자세 | 방어 여력을 소비해 정면 공격을 막고, 적극적으로 공격하면 여력이 회복되는 안 |

공격해서 방어 여력을 확보하고 중요한 공격을 막는 흐름을 목표로 한다. 바닥 공격·잡기 등 회피해야 하는 공격도 두어 방패만 들고 전투 전체를 해결하지 못하게 한다.

받아치기는 짧은 타이밍 대응, 방패 자세는 지속적인 방어 선택으로 차별화한다. 두 기능의 입력과 사용 상황이 실제로 겹치는지는 검토가 필요하다. 나머지 액티브 후보와 가드 판정·실패 시 손실은 미정이다.

### 4.3 궁수

이동 사격과 정밀 사격의 리듬 차이를 중심으로 한다. 언제 거리를 벌리고 언제 조준에 시간을 쓸지 판단하는 직업이다.

| 구분 | 가칭 | 동작과 사용 목적 |
|---|---|---|
| 중심 스킬 | 후퇴 사격 | 뒤로 물러나면서 사격해 거리 확보와 공격을 동시에 수행 |
| 중심 스킬 | 연속 사격 | 이동하면서 여러 발을 쏜다. 회피하며 압박을 유지 |
| 중심 스킬 | 관통 사격 | 조준한 방향으로 강한 화살을 쏜다. 일직선의 적과 노출된 약점 공략 |
| 중심 스킬 | 올가미 덫 | 접근하는 적을 늦추고 사격할 공간을 확보 |
| 고유 능력 | 집중 조준 | 조준을 유지하면 다음 정밀 사격이 강화되고, 크게 이동하면 집중이 풀리는 안 |

대표적인 흐름은 거리 확보 → 이동 사격으로 상황 관찰 → 안전한 순간 정밀 사격이다. 모든 전투에서 이 순서를 고정적으로 반복하도록 강제하지 않는다.

약점의 판정 방식, 집중 조준의 입력·해제 조건, 덫의 보스전 활용과 나머지 액티브 후보는 미정이다.

### 4.4 원소술사

화염과 냉기 두 원소를 초기 제안으로 둔다. 화염은 공격, 냉기는 공격할 상황을 만드는 쪽에 무게를 둔다. 적의 이동을 예측해 주문을 연계하는 직업이다.

| 구분 | 가칭 | 동작과 사용 목적 |
|---|---|---|
| 중심 스킬 | 화염탄 | 빠르게 발사하는 기본 주력 주문 |
| 중심 스킬 | 서리 파동 | 주변으로 냉기를 퍼뜨려 접근한 적을 늦춘다 |
| 중심 스킬 | 화염 지대 | 지정 위치에 불길을 만든다. 적이 머물 위치를 예측해서 사용 |
| 중심 스킬 | 얼음창 | 짧게 시전한 뒤 직선으로 강한 공격을 가한다 |
| 고유 능력 | 원소 융합 | 본인의 화염·냉기 주문을 연계하면 다음 주문에 추가 폭발이 발생하는 안 |

냉기로 움직임을 제한하고 화염 지대와 강한 주문을 맞히는 흐름을 목표로 한다. 준비하는 동안 적이 이동하면 공격 효율이 떨어지는 부담을 둔다.

보스처럼 제어가 제한되는 대상에게도 주문 연계가 성립해야 한다. 융합의 발동·입력 방식, 원소 조합 조건과 나머지 액티브 후보는 미정이다.

## 5. 스킬 수와 빌드 선택의 기준

선택 가능한 12~16개 중 8개를 장착하면서 공격 방식과 대응 능력이 달라지도록 한다. 같은 직업 안에서도 다른 구성이 성립하는 것이 목표다.

스킬을 추가할 때는 다음 차이를 설명할 수 있어야 한다.

- 짧은 빈틈과 긴 빈틈 중 언제 사용하기 좋은가.
- 근접·중거리, 단일 대상·다수 대상 중 어떤 상황을 담당하는가.
- 이동, 방어 대응, 제어, 자원 확보 등 공격 외에 어떤 선택을 제공하는가.
- 사용자가 감수하는 시전 시간, 공격 동작, 위치, 자원 부담은 무엇인가.
- 장착 슬롯을 차지하는 대신 어떤 다른 능력을 포기하게 되는가.

피해량과 재사용 대기시간만 조금 다른 공격기로 수량을 채우지 않는다. 상황에 따라 선택할 이유가 있고, 각 선택이 가진 부담도 드러나야 한다.

트라이포드는 선택한 스킬의 범위·타이밍·운용·자원 활용 등을 조정하는 방향으로 검토한다. 스킬 자체를 고르는 선택과 선택한 스킬을 변형하는 선택이 함께 의미를 가져야 한다. 개별 트라이포드 구성은 아직 정하지 않았다.

## 6. 구체화와 제작 순서 제안

### 6.1 지금 유지할 구조 기준

- 직업 소속·습득·편성·발동 자격을 구분하고 서버가 승인한다. 전투 편성의 최대 수는 8개이며 기본 공격·회피·고유 능력은 별도다.
- 스킬과 고유 능력의 부여·회수 주체를 명확히 한다. 시작·무기·직업 경로가 같은 기능을 중복 부여하지 않는다.
- 초기화·리스폰·편성 변경으로 중복 부여나 의도하지 않은 쿨타임 초기화가 발생하지 않게 한다. 공유 데이터와 시전별 실행 상태를 분리한다.
- SOLID와 책임별 모듈화를 따르고, 새 직업을 추가할 때 공통 캐릭터·스킬·UI에 직업별 분기를 늘리지 않는다.

### 6.2 나중에 구체화할 수 있는 내용

| 항목 | 결정할 시점 |
|---|---|

| 다른 직업의 전체 스킬·고유 능력 세부 구성 | 해당 직업을 구체화할 때. 다른 운용도 공통 구조로 표현되는지는 초기 설계에서 대조 |

### 6.3 권장 진행 순서

1. 기존 성장·편성·시전 구조에 직업 소속과 습득/발동 자격을 연결할 경계를 정한다.
2. Definition–Ability 연결, 시작·무기·직업의 부여 소유권, 현재 Pawn/ASC 초기화와 복원 계약을 구체화하며 필요한 기반을 구현한다.
3. 대검의 중심 스킬 몇 개부터 연결한다. 기존에 논의한 중심 4개를 출발점으로 삼을 수 있으며, 전체 후보 12개나 장착 8개를 모두 확정할 때까지 기다리지 않는다.
4. 기본 공격·회피·고유 능력과 함께 전투 감각을 보며 최대 8개 편성 구성을 점진적으로 완성한다.
5. 추가 후보와 트라이포드로 실제로 다른 구성이 성립하는지 확인하며 선택 가능한 12~16개 범위를 조정한다.
6. 두 번째 직업으로 궁수를 검토해 근거리의 공격 동작 부담과 원거리의 위치·조준 부담을 비교한다. 창방패 기사와 원소술사도 앞선 직업과 겹치는 부분을 조정하며 구체화한다.

이 순서는 현재의 제작 제안이다. 4개 직업 전체를 동시에 구현하기로 확정한 것은 아니다.

## 8. 코드 구조와 SOLID·모듈화 원칙

사용자가 명시한 필수 조건이다. 직업이 늘어날 때의 변경 범위와 기존 기능에 미치는 영향을 기준으로 구조를 검토한다. 클래스나 파일을 나누었다는 사실만으로 SOLID를 준수했다고 판단하지 않는다.

### 8.1 책임 경계

아래 신규 타입명은 구현 제안이다. 기존 스킬·퀵슬롯·장비 기능을 활용하고, 같은 상태를 여러 컴포넌트가 따로 소유하지 않도록 한다.

| 담당 | 구조와 책임 |
|---|---|
| 직업 정의 | 신규 `URPGPlayerClassDefinition`에 안정적인 직업 ID, 사용 무기 조건, 선택 가능한 스킬 참조, 기본 편성, 고유 능력 설정을 둔다. 공유 데이터에는 플레이어별 실행 상태를 저장하지 않는다. |
| 직업 적용 수명 | 신규 `URPGPlayerClassComponent`는 검증된 직업을 현재 Pawn/ASC에 적용하고 자신이 부여한 자원을 추적·회수한다. 스킬 성장 계산, 장비 변경, 스킬 실행과 UI 처리를 직접 구현하지 않는다. |
| 습득과 성장 | 기존 `URPGPlayerSkillComponent`의 레벨·SP·트라이포드 관리에 명시적인 습득 판정을 연결한다. 직업 소속과 습득 가능 여부는 직업 정의와 서버의 성장 상태로 판단한다. 카탈로그에서 Definition을 찾았거나 기본 레벨이 1이라는 사실을 습득 증거로 사용하지 않는다. |
| 전투 편성 | 기존 `UQuickSlotComponent`의 서버 소유 8슬롯을 편성 상태의 원본으로 사용한다. 직업 적용 컴포넌트와 UI에 별도의 현재 편성 목록을 만들지 않는다. 기본 편성 데이터는 최초 구성에만 사용한다. |
| 스킬 데이터와 실행 | 기존 `URPGSkillDefinition`과 시전별 `RuntimeSpec`, 공통 SkillContainer, 실행·타기팅 정책을 활용한다. 직업 이름을 보고 컨테이너가 서로 다른 전투 로직을 직접 실행하지 않는다. |
| 직업 고유 기능 | 투지 해방·방패 자세 등 다른 기능은 필요한 Ability·정책·활성화별 실행 객체로 구현한다. 모든 고유 능력을 하나의 거대한 직업 컴포넌트나 동일한 게이지 규칙에 넣지 않는다. |
| 장비·피격·표현 | 장비는 기존 장비 시스템, 피해·제어는 공통 전투 규칙, 표현과 입력은 각 기존 연결부가 담당한다. 직업 데이터는 필요한 설정을 제공하고 해당 시스템의 상태를 중복 관리하지 않는다. |

현재 시작 데이터와 무기 로드아웃도 Ability를 부여하고, 시작 데이터에는 고유 능력 부여 경로도 있다. 구현 시 공통 행동·직업 스킬·고유 능력·무기 고유 동작의 부여 주체를 명확히 정한다. 같은 스킬의 중복 부여·회수는 허용하지 않는다. 영속 선택은 캐릭터 저장 데이터로부터 검증해 복원하고, 현재 Pawn의 ASC와 부여 핸들은 해당 Pawn의 수명에 맞춰 관리한다.

### 8.2 SOLID 적용 기준

| 원칙 | 이 프로젝트에서 지킬 기준 |
|---|---|
| SRP — 단일 책임 | 직업 정의, 성장, 편성, 부여 수명, 시전 실행, 장비, 표현이 각자의 상태와 변경 이유를 가진다. 직업 적용 컴포넌트가 모든 기능을 구현하는 관리자로 커지지 않게 한다. |

| DIP — 의존성 역전 | 공통 코드가 대검·궁수 등 구체 직업을 참조하지 않게 한다. 직업 데이터, 필요한 기능 계약과 기존 정책을 통해 연결한다. 공통 전투 코드가 특정 직업 Widget이나 구체 플레이어 파생형을 요구하지 않게 한다. |

### 8.3 모듈과 의존 방향

- 직업별 기능은 공통 스킬·전투 계약을 사용한다. 공통 스킬·전투 코드는 구체 직업별 구현에 의존하지 않는다.
- 직업끼리 서로의 구현을 참조하지 않는다. 실제로 공유할 동작이 확인되면 해당 동작을 공통 정책이나 기능으로 추출한다.
- UI는 상태를 표시하고 서버에 변경을 요청한다. 스킬 사용 자격·피해·상태이상 판정의 원본은 서버의 게임플레이 계층이다.
- 처음에는 현재 Project_RPG 안에서 책임과 의존 방향에 따라 구성한다. 별도 UE 모듈·플러그인 분리는 실제 의존성과 독립 관리 필요가 확인될 때 판단한다.
- 인터페이스·기반 클래스·전략 객체는 실제로 필요한 교체 지점에 추가한다. 직업 수를 예상해 사용처 없는 범용 프레임워크를 먼저 만들지 않는다.

### 8.4 신규 직업 추가 시 확인할 결과

1. 새 직업 정의와 스킬 데이터, 필요한 고유 Ability·정책을 추가해 직업을 구성할 수 있어야 한다.
2. 기존 직업의 데이터와 구현을 수정하지 않아야 하며, 공통 캐릭터·UI에 새 직업의 이름이나 분기를 추가하지 않아야 한다.
3. 직업 소속·습득·편성·무기 조건 검사는 같은 서버 승인 경로를 사용해야 한다. 특정 직업의 별도 발동 경로로 우회하지 않는다.
4. 직업 적용·리스폰·회수 시 자신이 소유한 Ability와 효과만 처리하고, 다른 시스템의 부여나 이동 제한을 해제하지 않아야 한다.
5. 성장·편성 변경은 정한 적용 시점에 반영하고, 시전 중 `RuntimeSpec`을 뒤늦게 바꾸거나 편성 변경으로 쿨타임을 초기화하지 않아야 한다.

이 항목은 구현을 검토할 설계 기준이다. 현재 코드가 모두 충족하거나 검증이 완료됐다는 뜻은 아니다.

## 9. 재검토에서 확인한 누락과 보완 — 2026-10-25

아래 표는 구현 착수 전 조사 기록이다. 이후 6.3의 첫 단계인 직업 소속·명시적 습득·발동 자격 경계와 두 번째 단계인 Pawn/ASC 적용·부여 소유권·초기 슬롯 복원 경계의 C++ 기반을 추가했다. 후속으로 대검의 명시적인 개발용 기록 공급과 콘텐츠 생성 작업을 준비했다. 현재 구현/에셋 생성 상태와 아직 연결하지 않은 저장·콘텐츠는 [스킬 아키텍처의 최신 진행 기록](SKILL_AND_TRIPOD_MODULAR_ARCHITECTURE.md#2026-10-25-대검-개발용-기록-공급과-콘텐츠-생성-준비)에 구분해 기록한다. 이 절 전체가 구현됐다는 뜻은 아니다.

### 9.1 현재 코드와 설계 사이의 간극

| `UQuickSlotComponent::CanAssignSkillSlot`은 이미 부여된 Ability를 조회한다. 퀵슬롯 입력은 해당 Spec 핸들로 전달된다. | 8슬롯 배치만으로 직업 전체 스킬의 사용 제한이 완성되지 않는다. 서버의 발동 승인에서도 현재 편성을 확인해야 한다. |
| 시작 데이터가 시작 Ability와 `IdentityData.IdentityAbility`를 부여한다. 무기 로드아웃도 기본·특수 Ability를 부여한다. | 신규 직업 적용과 기존 시작·무기 경로 사이에 부여 소유권 이관이 필요하다. 고유 능력까지 포함해 중복을 방지한다. |
| SkillContainer의 `SkillDefinition`은 현재 BP 기본값으로 지정된다. 퀵슬롯 조회와 쿨타임 조회도 Definition을 사용한다. | 직업에 Definition 목록만 넣는 것으로 Ability 연결이 완료되지 않는다. 발동 이전부터 일관된 SkillTag·Definition·Ability Spec 연결을 제공해야 한다. |
| `UActivateIdentity`의 네이티브 발동은 부모 호출만 하고, `EndAbility` 본문은 비어 있다. | 현재 클래스를 완성된 고유 능력 공통 기반으로 간주하지 않는다. 사용 BP와 호출 경로를 확인하고, 재사용할 경우 부모 종료·취소 계약부터 정리한다. |
| 성장·슬롯 컴포넌트는 Pawn의 런타임 상태와 복제를 제공한다. | 이 구조 자체가 영속 저장·재접속 복원을 제공하는 것은 아니다. 저장 연동과 새 Pawn에 대한 복원 순서를 구현 범위에 명시한다. |

### 9.2 스킬 소유·부여·편성·발동을 구분

| 단계 | 원본과 의미 |
|---|---|
| 직업에서 선택 가능 | 직업 정의의 스킬 목록. 전체 카탈로그는 정의 검색용이며 사용 권한을 부여하지 않는다. |
| 습득 | 서버가 확인한 캐릭터 성장 상태와 해금 조건. 레벨·트라이포드 설정과 구분한다. |
| GAS 부여 | 서버가 현재 ASC에 구성한 Ability Spec. 부여된 사실만으로 모든 상황에서 발동할 수 있는 것은 아니다. |
| 편성 | 서버 소유 퀵슬롯의 최대 8개. 같은 SkillTag의 중복 등록과 무효한 슬롯을 거절한다. |
| 발동 가능 | 직업·습득·현재 편성·무기 조건과 기존 GAS 비용·쿨타임·생존·권한·행동 제한을 모두 만족한 상태. |

초기 구현 권장안은 **습득한 직업 스킬을 ASC에 부여하고, 편성된 최대 8개에만 발동을 허용**하는 것이다. 기존의 부여된 스킬 조회·편성 흐름을 활용하면서 편성 변경 때마다 Ability를 제거·재생성하지 않을 수 있다. 현재 자격 검사와 직업의 부여·회수·초기 슬롯 복원 경계를 연결하고, 대검 클래스/명시적 개발 프로필 에셋을 생성했다. 실제 저장·출시 초기 습득 정책과 플레이 검증, 고유 능력·최대 8개 편성 완성은 남아 있다.

- 직업 액티브 스킬의 사용 자격은 UI·편성 요청·발동 승인이 함께 참조하는 작은 공용 판정으로 둔다. UI가 숨겼다는 사실로 사용을 차단했다고 판단하지 않는다.
- 슬롯 입력 외의 직접 Ability 활성화나 이벤트 발동도 같은 사용 자격을 검사한다. 기본 공격·회피·고유 능력·패시브·피격 반응은 각자의 승인 규칙을 가지며, 8슬롯에 들어 있어야 한다는 조건을 일괄 적용하지 않는다.
- 공통 판정은 각 상태 소유자에게 필요한 값만 조회한다. 공통 전투 코드가 Widget이나 특정 직업 클래스에 의존하지 않게 한다.
- 편성 거절·복제 지연 때 UI는 서버 상태로 복원한다. 키를 누른 뒤 슬롯 구성이 바뀌어도 Release는 원래 Press를 받은 Spec에 전달한다.
- 전투·시전 중 편성/성장/트라이포드 변경은 초기에 거절하는 안을 권장한다. 허용 시점은 기획 결정이 필요하며, 허용 범위를 넓히더라도 기존 시전 스냅샷과 쿨타임을 변경해 이득을 얻을 수 없어야 한다.

### 9.3 정의 연결과 부여 소유권

- 초기에는 기존 스킬의 Definition을 설정한 Ability BP를 활용하는 안을 우선 검토한다. 직업의 스킬 참조와 부여할 Ability가 같은 SkillTag·Definition을 가리키는지 확인한다. 수치·트라이포드 차이를 위해 새 네이티브 Ability 클래스를 만들지 않는다.
- 여러 Definition을 동일 컨테이너 클래스에 런타임으로 연결하는 방식을 채택한다면, 부여별 연결 정보를 발동 가능 여부·퀵슬롯·쿨타임 조회 이전에 해석해야 한다. 공유 CDO의 Definition을 바꾸거나 `ActivateAbility`에서 처음 연결하는 방식은 사용하지 않는다.
- 현재 Ability Spec의 `SourceObject`에는 Pawn이나 무기가 들어가는 경로가 있다. 이를 Definition으로 바꾸는 경우 부여 출처·효과 컨텍스트·기존 조회에 미치는 영향을 먼저 확인한다.
- 공통 이동·상호작용은 공통 시작 경로, 직업 액티브·고유 능력은 직업 적용 경로, 무기의 실제 고유 동작은 무기 경로로 소유권을 나누는 안을 기준으로 이관한다. 이미 운영 중인 공격의 부여 주체를 이름만 보고 일괄 변경하지 않는다.
- 부여 계획을 먼저 검증하고 전환할 스킬의 기존 소유 핸들만 이관한다. 전체 Ability/Effect 제거로 다른 시스템의 자원을 회수하지 않는다. 실패 시 같은 직업을 다시 적용해 중복 부여하는 상태나 반만 적용된 상태를 남기지 않는다.

### 9.4 초기화·복원·콘텐츠 변경의 수명

1. 서버가 캐릭터의 직업·성장·편성 기록을 확인하고 필요한 정의를 로드한다. 로딩 중과 새 캐릭터의 빈 기록을 구분하며, 기본 편성은 명시적인 최초 생성에만 적용한다.
2. 현재 Pawn/ASC의 준비와 정의 로드가 모두 완료되면 검증된 구성을 적용한다. 같은 초기화가 반복돼도 같은 소유 핸들이 중복 부여되지 않게 한다.
3. 비동기 완료와 Ability 콜백은 아직 같은 캐릭터·Pawn·적용 요청인지 확인한다. 재접속·리스폰·권한 회수 뒤 도착한 오래된 완료가 구성을 덮어쓰지 못하게 한다.
4. 사망, 같은 Pawn의 부활, 새 Pawn의 리스폰, 던전 재도전, 재접속을 구분한다. 고유 자원·버프·쿨타임의 보존/초기화는 각 사건별 규칙으로 정한다. 무기·슬롯 교체나 재부여를 쿨타임 초기화 수단으로 만들지 않는다.
5. 사용 중인 장판·투사체·차지·고유 능력의 종료와 효과·이동 제한 해제는 해당 실행과 소유자가 처리한다. 사망·장비 변경·직업 변경 후 어느 실행을 유지할지도 명시한다.
6. 직업 ID·SkillTag·트라이포드 선택·8슬롯을 저장할 식별자와 데이터 버전을 정한다. 배열 순서나 표시 이름을 영속 식별자로 사용하지 않는다. 현재 트라이포드 인덱스를 저장할 경우 옵션 순서 변경 시 변환이 필요하다.
7. 삭제·이름 변경된 스킬, 무효한 트라이포드, 달라진 SP 비용을 복원할 때의 변환·환급 규칙을 마련한다. 사용 SP는 서버의 유효한 성장 기록으로 다시 계산하고, 저장 실패를 신규 캐릭터 기본값 저장으로 덮지 않는다.

정의의 누락·중복 SkillTag·잘못된 기본 편성·지원하지 않는 실행 설정은 기존 에셋 검증 경로로 확인한다. 미리 보기용 UI 표시는 정의 로딩 상태를 표현하며, 로딩되지 않은 필수 데이터로 게임플레이를 승인하지 않는다. 전체 선택 데이터는 소유자에게, 다른 플레이어에게 필요한 직업·무기·반응 표현 상태는 해당 범위로 복제한다.

### 9.5 게임 디자인과 제작에서 더 정할 부분

| 항목 | 빠져 있던 결정과 검토 기준 |
|---|---|
| 전투 구성 변경 | 전투 판정의 기준, 시전 중 변경 허용 여부, 직업 변경 장소와 조건을 정한다. 초기 구현에 자유로운 실시간 직업 교체를 포함하지 않는 안을 권장한다. |
| 비용·취소 | 차지 시작·발사·적중 중 비용과 쿨타임을 언제 확정하는지, 취소·빗나감·중단 때 무엇을 돌려주는지 정한다. 공통 기본 규칙과 데이터로 표현할 예외를 구분한다. |
| 고유 능력 입력 | 투지 해방의 사용, 방패 자세의 유지, 집중 조준의 조건, 원소 융합의 자동/수동 발동을 각각 정한다. 고유 능력 1개가 반드시 같은 버튼 방식이나 단일 숫자 게이지를 뜻하지 않는다. |
| 기본 능력치와 무기 | 직업 기본값·성장·장비 보정의 계산 원본을 정한다. 무기를 바꿔도 직업 자체가 바뀌지 않으며, 무기 요구를 잃었을 때 제한할 공격과 유지할 공통 행동을 구분한다. |
| 보스 대응 | 궁수의 약점이 별도 부위 판정인지 공격 기회인지, 덫·냉기가 제어 면역 보스에게 어떤 쓸모가 있는지 정한다. 새 피격·상태이상 규칙이 지원하는 범위에 맞춘다. |
| 파티 조합 | 특정 직업이 없는 조합과 같은 직업이 여럿인 조합에서도 공략이 성립하는지 검토한다. 보호·표식·원소 효과의 중첩/갱신/출처 규칙으로 특정 조합의 필수화를 방지한다. |
| 전투 거리와 표현 | 근접·원거리의 실제 공격 기회와 위험을 함께 비교한다. 무기·스켈레톤·몽타주·조준·카메라·효과·고유 능력 UI의 필요 자산과 기존 연결부를 직업별로 확인한다. |

코드 구현에 착수할 때는 **습득/발동 자격 → Definition 연결과 부여 소유권 → 초기화/복원 계약 → 대검 중심 스킬 몇 개 → 최대 8개 편성 구성으로 확장** 순서로 진행한다. 세부 기획의 결정 시점은 6절을 따른다. 신규 직업 확장성을 확인할 때는 궁수 같은 다른 운용의 직업도 같은 계약으로 표현되는지 설계 수준에서 대조하고, 첫 직업 구현을 위해 불필요한 새 테스트 도구나 범용 프레임워크를 추가하지 않는다.
