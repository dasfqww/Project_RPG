# Project RPG Codex 구독 작업자 운영 계획

현재 사용하는 Codex를 기획·개발·아트 조정·QA 검토 작업자로 연결한다. 사용자는 하루 1회 결과를 검토하고, 관리 프로그램이 작업 선택·실행·복구·게시를 맡는다. [전체 제작 계획](CONTINUOUS_GAME_PRODUCTION_PLAN.md)의 PROD-04와 PROD-11을 구체화한 문서이며, 계획 작성 단계다. 실제 모델 호출·계정 설정 변경·상시 실행은 아직 수행하지 않았다.

## 초기 운영 결정

| 항목 | 초기 정책 |
|---|---|
| AI 공급자 | Codex 단독. Claude 도입은 선택 확장 |
| 인증 | 사용자가 직접 공식 CLI에 로그인한 ChatGPT 구독 인증 |
| 동시 실행 | 파이프라인이 시작하는 Codex는 최대 1개. 역할마다 별도 세션 |
| 추가 지출 | 유료 API 자동 전환·크레딧 구매·요금제 변경 기본 비활성 |
| 모델 | 실제 계정에서 사용 가능한 모델을 M0에서 명시 고정. 실행 중 임의 변경 없음 |
| 검토 | 사용자 하루 1회. 시각 미정, 20~30분은 제안 |
| 런타임 | 관리 프로세스가 작업자를 시작하고 종료 상태를 수집. 긴 대화 하나를 계속 연장하지 않음 |
| 완료 | 실제 산출물과 검사 결과, 정리, 기능별 커밋·푸시·원격 확인으로 판정 |

이 동시 실행 제한은 파이프라인 내부에 적용한다. 사용자의 앱/IDE 대화와 다른 담당 작업은 별도로 계정 사용량을 소비할 수 있으며, 관리 프로그램은 이들을 종료하거나 인증을 변경하지 않는다. 모든 역할의 사용량은 같은 계정 기준으로 관리하고 역할별 별도 구독 한도를 가정하지 않는다.

## 확인한 실행 조건

2026-11-10 현재 사용자 환경의 읽기 전용 확인 결과다.

| 확인 | 결과 | 해석 |
|---|---|---|
| `codex --version` | `codex-cli 0.144.3` | 이 버전으로 어댑터 호환 검증을 시작 |
| `codex login status` | 종료 0, `chatgpt` 인증 방식 | 로그인 상태 확인. 실제 모델 요청/구독 등급/잔여량 확인은 아님 |
| `codex exec --help` | `--json`, `--output-schema`, `--output-last-message`, `--cd`, `--ignore-user-config`, `resume` 지원 | 명령과 결과 수집 설계의 기반 |
| 인증 취급 | 상태 명령의 성공/방식만 기록 | 비밀 파일·토큰 원문 읽기/로그 출력 없음 |

[OpenAI 인증 문서](https://learn.chatgpt.com/docs/auth)는 ChatGPT 구독 로그인과 API 인증을 구분한다. [비대화식 실행 문서](https://learn.chatgpt.com/docs/non-interactive-mode)는 저장된 CLI 인증을 재사용하는 실행과 신뢰할 수 있는 환경의 계정 기반 자동화를 설명한다. 자동화의 일반적인 권장 인증은 API 키이지만, 이 프로젝트는 기존 구독 사용을 목표로 계정 방식의 가동 조건부터 검증한다.

현재 로그인 상태가 별도 Windows 서비스 계정에도 적용된다고 가정하지 않는다. 초기 Codex 작업자는 공식 로그인을 마친 같은 Windows 사용자 문맥에서 실행한다. 관리 프로세스를 다른 계정으로 운영하더라도 작업자는 해당 사용자 문맥의 로컬 연결로 호출한다. 자동 부팅과 로그온 후 작업자 준비를 구분하고, 계정 문맥이 준비되지 않으면 `NeedsLogin`으로 대기한다.

## 역할과 실행 순서

| 역할 ID | 입력 | 결과 | 허용된 작업 |
|---|---|---|---|
| planner | 승인 목표·현재 계약·채택된 방향 | 명세 revision, 작업 카드, QA 기준 | 지정한 기획/작업 문서 작성 |
| art-director | 아트 브리프·에셋 규격·기존 소재 | 후보 지시, 기술 검사와 엔진 적용 계획 | 지정한 아트 작업과 허용된 제작 도구 호출 |
| developer | 고정 명세·기반 커밋·수정 경로 | 코드/설정/회귀 검사와 인계 정보 | 격리 작업 공간의 예약 경로 편집 |
| integrator | 같은 revision의 코드와 아트 | 실행 빌드·에셋 manifest | 승인된 임포트/빌드 작업 제출 |
| qa-reviewer | 고정 기준·diff·실제 실행 근거 | 결함 카드 또는 검증 판정 | 제품 입력 읽기, QA 결과 작성, 등록된 검사 제출 |
| reporter | 확정된 작업/검사/게시 기록 | 하루 검토 요약 | 요약 작성. 원본 검사 결과 변경 불가 |

첫 사이클은 `planner → art-director/developer의 준비된 작업 → integrator → 실제 테스트 → qa-reviewer → 게시 → reporter` 순서다. 아트 생성이나 빌드가 외부에서 실행 중일 때, 수정 경로와 고정 입력이 독립적인 다음 Codex 작업을 선택할 수 있다. 아직 통합되지 않은 결과를 후속 QA의 성공 입력으로 삼지 않는다.

검토자는 새 세션으로 명세·실제 diff·원본 검사 결과를 받는다. 개발자의 대화 전체나 자기평가를 검토 근거로 삼지 않는다. 동일 모델의 관점 중복은 남으므로 서버/클라이언트 실행·실제 화면·수치 검사와 사용자 플레이 검토를 통과 기준으로 유지한다.

기획 세션이 완료 기준을 작성하고 개발 세션이 구현한다. QA 실패가 나오면 먼저 코드/에셋/검사도구/명세 중 원인을 분류한다. 명세 자체를 바꿔야 할 때만 새 revision과 사용자 결정 항목을 만들며, 이미 승인된 명세를 만족시키는 수정은 자동으로 계속한다.

## 작업자 실행 계약

관리 프로그램은 다음 공통 동작을 가진 `CodexWorker` 어댑터를 구현한다. 명칭은 내부 인터페이스 설계이며 기존 CLI의 실제 API 이름을 뜻하지 않는다.

| 동작 | 책임 |
|---|---|
| Inspect | CLI 버전·실행 가능 여부·인증 방식과 관측 시각 확인 |
| Start | 고정 작업 카드와 작업 디렉터리로 새 실행 시작, attempt ID/PID 기록 |
| Observe | JSONL 사건·종료 코드·결과 schema를 수집하고 정규화 |
| Checkpoint | 종료/중단 시 관리자 측 diff·산출물·검사·인계 상태 고정 |
| Resume | 같은 task/role/input revision의 명시 session ID만 재개 |
| Stop | 소유 실행의 종료와 파일 사용 해제 후 정리 |

실행 입력에는 task/attempt ID, 역할, 명세 revision, 기반 커밋, 읽기 입력 해시, 쓰기 허용 경로, tool 권한, 결과 schema, 실행 시간/시도 한도를 넣는다. 프롬프트에는 해당 작업의 [AGENTS.md](../AGENTS.md)와 필요한 계약을 포함한다. 사용자 지시의 우선순위를 보존하고, 작업 카드가 기존 공통 규칙을 완화하지 못하게 한다.

최종 결과의 필수 필드는 `task_id`, `attempt_id`, `role`, `spec_revision`, `input_manifest_hash`, `outcome`, `artifact_manifest`, `validation_refs`, `handoff`, `block_reason`이다. `outcome`은 작업자의 보고이고 완료 상태를 직접 변경하는 권한이 아니다. 관리자는 실제 diff/해시/검사 기록과 대조해 다음 상태로 이동한다.

설치된 CLI의 `--json`, `--output-schema`, `-o`, `--cd`를 사용해 사건·최종 결과·실제 파일을 연결한다. 셸 문자열로 프롬프트와 경로를 이어붙이지 않고 인자 배열과 stdin을 사용한다. 실험용 플래그나 문서에만 있고 설치 버전에 없는 옵션은 사용하지 않는다. 자동 업데이트는 기본 비활성이고, 버전 변경 시 어댑터 회귀를 다시 수행한다.

사용자 설정의 API 공급자/유료 도구가 무심코 섞이지 않도록 작업 전용 실행 설정을 검증한다. 설치 버전의 `--ignore-user-config`는 사용자 config 생략 수단일 뿐 모든 프로젝트 설정/관리 정책/환경변수까지 제거하는 기능으로 취급하지 않는다. 작업자 프로세스에 전달하는 환경과 프로젝트 설정까지 확인한다. 부모 환경변수나 사용자 설정을 직접 변경하지 않는다.

작업자의 쓰기 범위는 프롬프트뿐 아니라 격리 작업 공간, 도구 권한, 파일 접근 정책으로 제한한다. 실제 OS/CLI 제한이 동작하는지는 가동 전 검사한다. 빌드/에셋 변경/외부 생성은 자원 임대를 가진 등록 어댑터로 제출한다. Git 게시·정리·예약 해제는 관리자가 맡아 작업자가 부분 성공만으로 Done을 기록하지 못하게 한다. 이 위임은 기능별 커밋·푸시 의무를 없애지 않는다.

## 로그인과 과금 경로

초기 정책은 `SubscriptionOnly`다. 공식 로그인 절차는 사용자가 수행하고, 관리 프로그램은 비밀번호·인증 토큰을 자체 DB에 저장하지 않는다. 계정 정보는 로컬 별칭, 공급자, 인증 방식, 준비 여부, 관측 시각만 저장한다. 공식 CLI의 인증 보관과 갱신을 사용한다.

가동 전에는 같은 작업자 사용자 문맥과 실행 환경에서 아래 조건을 확인한다.

1. ChatGPT 구독 인증이 실제 선택됐고, 명시 API 키/사용자 정의 공급자/다른 과금 프로필로 대체되지 않았는지 확인한다. 키가 있는지 확인할 때도 값은 출력하지 않는다.
2. 로그아웃/계정 변경/토큰 철회가 감지되면 신규 배정을 중지한다. 원래 사용자 계정을 자동으로 로그아웃시키거나 다른 계정으로 회전하지 않는다.
3. 추가 크레딧의 자동 사용·자동 충전·워크스페이스 청구 정책을 확인한다. API 자동 전환 금지만으로 추가 비용이 0이라고 표시하지 않는다.
4. 한 실행 안에서 포함 한도와 추가 크레딧 사이 전환을 확실히 제한할 수 있는지는 M0에서 검증한다. 엄격한 추가 비용 0을 보장할 제어가 없으면 그 조건의 무인 운영을 활성화하지 않는다. 별도 비용 범위를 사용자가 설정한 경우에만 해당 범위로 운영한다.
5. 최초 읽기 작업과 격리 파일 변경 작업의 실제 호출·인증·결과 수집을 확인한다. 로그인 상태 조회만으로 이 검사를 대체하지 않는다.

[공식 사용량 안내](https://learn.chatgpt.com/docs/pricing)에 따라 현재 한도는 usage dashboard 또는 CLI의 `/status`에서 확인할 수 있다. `/status`를 비대화식 `codex exec`의 구조화된 잔여량 API로 가정하지 않는다. 공식적으로 제공되는 관측 수단이 설치 버전에서 확인될 때만 자동 수집하고, 관측하지 못하면 Unknown으로 기록한다. 토큰 사용량과 구독 잔여량은 별도 값이다.

구독료는 고정비, 추가 크레딧·API·외부 생성은 별도 사용비로 기록한다. 아직 확인되지 않은 사용비는 0원 대신 Unknown이다. 사용자와 다른 도구의 사용까지 포함한 계정 전체 상태를 관리자 내부 장부만으로 정확히 재현한다고 주장하지 않는다.

## 계정 상태와 대기 정책

| 상태 | 배정/복구 동작 |
|---|---|
| Ready | 인증/과금 경로가 확인됐고 현재 배정 가능. 남은 정확한 수치는 별도 표시 |
| Busy | 파이프라인 Codex 실행 1개가 점유. 완료/체크포인트를 기다림 |
| QuotaWaiting | 명시 한도 응답에 따라 신규 AI 배정 중지, 알려진 재개 시각 이후 재확인 |
| NeedsLogin | 인증 실패 또는 필요한 사용자 문맥 부재. 일일 검토 화면에 로그인 필요 표시 |
| Backoff | 일시적 네트워크/서비스 오류. 제한된 지연 재시도 |
| ConfigurationBlocked | 미지원 CLI·모델·권한·확인되지 않은 과금 경로. 설정 수정 필요 |
| Unknown | 오류 분류나 사용량 신호가 불명확. 무한 재시도/유료 전환 없이 원인 기록 |

오류는 종료 코드만으로 한도/인증 문제라고 단정하지 않는다. 버전별 구조화 사건과 검증된 오류 패턴을 결합한다. 처음 보는 결과 형식은 Unknown으로 처리한다. 원문 로그는 비밀정보를 제거한 최소 범위만 남긴다.

QuotaWaiting의 재개 시각을 공급자가 제공하면 그 시각을 우선한다. 시각을 모르면 초기 재확인 간격은 30분, 최대 2시간으로 늘린다. 사용량을 소비할 수 있는 모델 호출을 단순 상태 확인용으로 반복하지 않는다. 비과금 상태 확인 수단이 없으면 다음 일일 검토에서 재개 여부를 확인한다. 이 간격은 프로젝트 운영 설정이며 구독의 실제 초기화 주기를 의미하지 않는다.

일시적 오류는 초기 1분/5분/15분 간격으로 추가 3회까지만 재시도한다. 같은 제품 결함의 자동 수정은 원 계획의 추가 2회 제한을 공유한다. 세션을 새로 열어도 시도 횟수를 초기화하지 않는다.

AI가 대기하는 동안 이미 정의된 빌드·테스트·렌더·산출물 정리를 수행할 수 있다. 모든 실행 가능한 작업이 끝나면 서비스는 대기한다. 같은 구독으로 역할만 바꿔 한도를 우회하거나, 승인되지 않은 계정/API로 전환하지 않는다.

## 중단과 역할 간 인계

인계 묶음은 작업 ID, 명세 revision, 기반/현재 커밋, diff 해시, 수정 파일, 확인된 사실, 남은 작업, 검사별 실제 결과, 외부 task ID, 소유 자원과 미확정 동작을 포함한다. 명령 성공·로그 문구·구현자의 추정과 실제 검사 통과를 구분한다.

- 정상 인계: 산출물을 저장하고 관리자 검증 후 다음 역할을 새 세션으로 시작한다.
- 같은 작업 재개: 파일·명세·세대가 일치할 때 명시 session ID로 재개한다. 전역 `--last`로 다른 작업의 대화를 선택하지 않는다.
- 세션 유실: 관리자 측 인계 묶음과 실제 diff로 새 세션을 시작한다. 대화 원문이 유일한 작업 기록이 되지 않게 한다.
- 한도/크래시 중단: 에이전트가 요약을 남기지 못해도 관리자가 소유 프로세스 종료와 작업 디렉터리를 확인해 부분 변경을 보존한다. 실패한 작업을 기능 완료로 커밋하지 않는다.
- 자원 회수: GPU·빌드·Git 임대는 실제 사용 종료 후 반환한다. 부분 변경이 남은 작업 디렉터리와 제품 경로 예약은 복구/인계가 끝날 때까지 다른 쓰기에 재할당하지 않는다. 독립 경로의 작업은 계속한다.
- 결과 변경: 검토 대상 diff·바이너리·에셋이 바뀌면 해당 검증을 무효화한다. 실패 검사의 예상값을 임의로 낮추지 않는다.

## 첫 일주기의 구체적인 예

시각은 사용자가 하루 검토 시각 T를 정한 뒤 배치한다. 아래는 순서 예시이며 각 단계를 24시간 안에 끝낸다는 약속이 아니다.

1. 일일 검토: 봉인석의 외형 기준·동작·완료 조건과 다음 작업 우선순위를 확정한다.
2. planner: 명세와 P01~P08 검사 입력을 고정한다. 미정 선택은 별도 항목으로 남긴다.
3. art-director: 기존 허용 소재나 절차적 초안으로 배치/규격을 준비한다. 외부 생성 권한과 비용이 정해졌다면 그 범위의 새 모델·아이콘을 만든다.
4. developer: 봉인석 서버 동작과 클라이언트 표시를 구현하고 유지할 검사를 추가한다.
5. integrator와 러너: 동일 입력으로 임포트/빌드·두 클라이언트 검사를 실행한다. 그동안 Codex는 독립된 다음 작업을 할 수 있다.
6. qa-reviewer: P01~P08의 원본 결과와 실제 화면을 검토하고 결함이면 해당 담당 역할로 되돌린다.
7. 관리자: 통과 기능의 임시 정리·커밋·푸시·원격 확인을 마치고 일일 묶음에 넣는다.
8. reporter: 확정 기록을 요약한다. AI 한도 대기 중이면 관리자가 정형 결과 목록을 제공하고 AI 요약은 생략한다.

예산이 정해지기 전 기존 소재·절차적 초안은 파이프라인 연결 검증에 사용할 수 있다. 이 결과를 새 AI 아트 제작 완료로 세지 않는다. 최초 전체 제작 완료에는 새 원본 아트가 실제 엔진에 적용되고 검토를 통과한 근거가 필요하다. ChatGPT 구독에 별도 3D 서비스 사용권이 포함됐다고 가정하지 않는다.

## 작업자 기능의 구현 순서

| 하위 단위 | 포함 범위 | 완료 기준 |
|---|---|---|
| PROD-04A | 실행 환경·인증/과금 방식 검사와 Codex 단일 호출 | 실제 읽기 작업의 구조화 결과 수집, 잘못된 계정/설정에서 배정 거절 |
| PROD-04B | 역할별 입력/결과 schema와 격리 변경 | 기획 → 개발 → 새 검토 세션 인계, 허용 경로 밖 변경 차단 |
| PROD-04C | 한도/인증/오류 분류와 복구 | QuotaWaiting/NeedsLogin/Backoff 분기, 부분 변경/시도 횟수 보존 |
| PROD-04D | 기존 QA·Git 관리자 연동 | 검증 실패·공유 자원 충돌·원격 선행 시 잘못된 Done 차단 |
| PROD-11A | 동일 사용자 작업자 가동과 일일 상태 화면 | 로그온/재시작/세션 부재 복구, 한도 관측 시각과 대기 이유 표시 |
| PROD-11B | 실제 운영 표본과 72시간 관찰 | 계정 사용량·AI 가동/대기·빌드/QA·개입·비용을 분리 기록 |

운영 표본은 실제 작은 작업 3개로 시작해 토큰·실행 시간·검사 시간·재작업·한도 대기를 측정한다. 동시 실행 확대나 두 번째 공급자 도입은 이 결과에서 병목이 확인될 때 판단한다. 현재 요금제를 추측해 하루 처리량을 약속하지 않는다.

## 가동 전 검증 목록

다음은 후속 구현의 수락 조건이며 이번 문서 작업에서 실행한 결과가 아니다.

| ID | 시나리오 | 통과 조건 |
|---|---|---|
| A01 | 실제 구독 실행 | 같은 사용자/설정에서 실제 요청·구조화 결과·인증 경로 확인 |
| A02 | 유료 경로 혼입 | 테스트 환경의 API/공급자 설정 혼입을 배정 전 거절, 실제 유료 요청 0 |
| A03 | 계정 한도 도달 | 모의 공급자 사건으로 대기/재개 동작 확인. 실제 관측이 없으면 모의 검증으로 표기 |
| A04 | 재로그인 필요 | 실제 계정을 로그아웃시키지 않는 fixture로 NeedsLogin 전환과 복구 확인 |
| A05 | 부분 수정 중 종료 | 소유 작업자만 중단해 diff 보존, 새 세션 재개, 미완료 변경 게시 차단 |
| A06 | 중복 실행/오래된 결과 | 한 슬롯만 점유, 이전 세대 결과의 게시 거절 |
| A07 | 검토 불일치 | 코드 변경/검사 누락/입력 해시 변경을 성공으로 승인하지 않음 |
| A08 | 출력/버전 오류 | 깨진 JSON·누락 schema·미지원 CLI를 Unknown/설정 오류로 처리 |
| A09 | 자원과 사용자 보호 | 사용자 에디터·기존 대화·타 담당 파일을 유지하며 자기 임시만 정리 |
| A10 | 재부팅/사용자 세션 | 작업자 문맥 부재에서 대기, 준비 후 중복 없이 재개 |
| A11 | 게시 응답 유실 | 원격 ref 확인으로 기존 커밋을 복구, 중복 커밋·강제 푸시 없음 |
| A12 | 추가 비용 정책 | 실제 계정의 포함량/추가 크레딧/API 구분과 허용 범위 확인. 미확인 상태를 0원으로 표시하지 않음 |

요금제와 잔여 한도, 검토 시각, 별도 아트 비용은 운영 입력으로 남아 있다. 이 입력이 없어도 큐·schema·오류 분류·복구 기능은 구현할 수 있다. 실제 구독 기반 상시 가동은 A01/A02/A12를 포함한 계정 조건과 전체 제작 계획의 환경 조건을 충족한 뒤 시작한다.
